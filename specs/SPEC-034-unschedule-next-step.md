# SPEC-034：取消排期与未举行后的连续下一步

- 状态：`Accepted`
- 创建：2026-09-02
- 优先级：P2
- 关联：SPEC-007、SPEC-011、SPEC-023、SPEC-025、SPEC-030

## 1. 已复现

从活动详情执行“取消排期”或“未举行 / 重新排期”成功后，Topic 已变为 `CLAIMED`，但活动详情仍停留在“活动已取消或状态变化”的死页，所有业务动作消失；从周历进入时，背景事件也已消失。尤其“未举行 / 重新排期”按钮明确承诺重新排期，却没有对应下一步。

## 2. 产品逻辑

- 未来 `UPCOMING` 的“取消排期”表示计划暂缓：完成报名通知确认并成功后关闭失效活动详情，进入 `CLAIMED + list`、清除临时条件并聚焦目标卡；不自动打开排期，以免刚取消又被催促重排。
- 已结束 `ENDED` 的“未举行 / 重新排期”表示确认本次未发生并准备择期：成功后关闭失效活动详情，使用服务端返回的最新 `CLAIMED` revision 直接进入可关闭的排期表单。
- 连续排期表单明确说明“未举行状态已保存，旧报名已清理；现在可重新安排，时间未定可关闭后从准备中继续”。它不自动提交、不恢复旧报名、不重复执行 unschedule。
- 从列表执行相同动作遵守同一下一步；关闭转场后按 SPEC-025/030 聚焦准备中卡片。
- 若动作来自高密度日历的完整当日议程，成功后同时结束议程、详情和确认层的旧上下文；未举行进入新排期弹窗，未来取消进入 `CLAIMED` 卡片，且等待 1 秒后不被外层议程回焦覆盖。

## 3. 失败与并发

- 通知名单、确认与 412 刷新继续遵守 SPEC-023；只有 unschedule mutation 真实成功后才能进入下一步。
- 后续排期失败保留草稿并遵守 SPEC-027 与同日单轨；关闭不回滚已成功的“未举行”。
- 活动详情不得保留为失效叠层，也不得让焦点穿透到不可见日历事件。

## 4. 验收

桌面与 Pixel 7 从列表、NEXT/周历详情分别完成未来取消与结束未举行：未来取消进入准备中卡并稳定聚焦；结束未举行进入一次排期表单，关闭后卡片仍为 `CLAIMED`，重试可排期；旧参与名单清空且通知责任不回退。请求计数证明 unschedule 与后续 schedule 都只在用户各自显式确认时发送一次。
