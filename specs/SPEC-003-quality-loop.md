# SPEC-003：独立 Agent 质量收敛循环

- 状态：`Accepted`
- 创建：2026-09-01
- 最后更新：2026-09-02

## 1. 目标

通过彼此独立的产品、后端和体验审查，持续发现一个最值得实现的需求或最有必要修复的 BUG；每轮只引入一个主要变量，完成规格、开发和验证后再进入下一轮，直到项目质量收敛。

## 2. 每轮流程

1. 启动必要数量的独立 agent，默认覆盖产品价值、数据正确性、交互/可访问性。
2. 每个 agent 只推举 1 项，必须包含证据、用户影响和验收标准，不直接改代码。
3. 主 agent 按以下顺序选择本轮唯一最高优先级项：
   - P0 数据丢失、安全或服务不可用
   - P1 核心流程错误、并发一致性、明确需求不可用
   - P2 显著提升完成率或可访问性的功能
   - P3 纯视觉或便利性优化
4. **先更新对应规格**，写入复现路径/需求和验收标准。
5. 开发、添加回归测试、完成构建和浏览器验证。
6. 将验证证据回写规格，然后开始下一轮独立审查。

## 3. 停止条件

质量循环不得因“核心功能已经存在”或单轮未发现严重问题而提前结束。只有同时满足以下全部条件时才能终止：

- **连续两轮**独立审查均没有发现新的 P0/P1，也没有仍然有明确用户价值、逻辑合理且可在当前产品边界落地的 P2。
- 每轮至少覆盖产品流程、数据/API 正确性、浏览器交互与“页面承诺—真实功能”四个视角；审查者必须提供证据，不能只运行现有测试后宣布无问题。
- 从用户视角完成“发起 → 认领/自领 → 准备 → 排期 → 参会/宣讲 → 归档 → 查看沉淀”的端到端旅程，并明确每个状态的允许动作、撤销/纠错路径和失败反馈。
- 页面上所有按钮、链接、导航、状态提示和功能性文案均已建立“可见承诺 → 规格 → 实现 → 浏览器验收”的追溯；不能存在有文字无功能、死入口或名不副实的统计/状态。
- 没有未实现的用户明确需求；新增的合理功能完成规格、实现、自动化、桌面/移动浏览器验收和部署验证。
- 当前全部规格的自动化和浏览器验收通过，依赖审计没有 moderate 及以上漏洞，生产服务健康。
- 剩余项只能是低价值视觉偏好、需要用户业务决策/外部权限，或明确超出产品定位；每一项都必须写明证据与不实施理由。

连续轮次按严格门槛计数：只有该轮独立审查没有新增 P0/P1/合理高价值 P2，且端到端操作、页面承诺、规格追溯和生产验证均已闭环，才计为 1 个“无新增有效轮次”。任一审查发现上述候选，或任一闭环尚未完成，连续计数立即归零；修复和部署本身不计作无新增轮次，必须在其后重新独立审查。

终止时必须输出完整的功能成熟度清单、验证证据和剩余边界，不能默默忽略，也不能以时间、工作量或循环轮数作为停止理由。

## 3.1 页面承诺审查清单

每轮浏览器审查至少逐项检查：顶部导航、Hero/Closing CTA、统计卡片、状态筛选、搜索、排序、列表卡片动作、月/周日历、弹窗、资料/会议链接、流程说明和 Footer。任何暗示可操作或可到达结果的文字，都必须满足以下之一：

1. 入口可操作并完成对应业务结果，有成功/失败反馈和浏览器验收；
2. 明确标注为站外/线下说明，不伪装成站内功能；
3. 删除或改写误导性文案。

## 3.2 全量回归的隔离与业务落点

- 依赖真实限流窗口、倒计时或多页面协作的浏览器用例，超时预算必须覆盖测试环境窗口、页面交互和 `finally` 清理；不得让通用短超时在清理前关闭 request/context。
- 会创建排期、报名或归档数据的用例必须在成功和失败路径都完成回收。若全量回归发生连锁失败，先修复并单独复验第一个破坏隔离的根因，不把后续时间冲突误判成多个产品缺陷。
- 用例要制造“页面持有陈旧快照 → 外部协作者先修改”的冲突时，必须先断言旧动作已经真实渲染，再发外部请求；不得让页面首次加载与外部写入竞争，否则测试可能从未建立要验收的陈旧状态。
- 浏览器断言必须跟随当前业务规格：创建成功后落点是刚创建的议题卡；只有用户主动关闭未提交弹窗时才恢复原触发入口。不得用历史交互断言阻止已验收的业务落点。
- 全量回归只有在无失败、无重试残留且测试数据库可继续独立运行时才算通过；定向用例通过不能替代完整回归。

### BUG-CONC-001 生命周期转换竞态

复现条件：两个连接同一 SQLite 文件的服务实例，同时读取同一 `OPEN` 议题并提交不同认领人。旧实现先 `SELECT` 校验、再按 `id` 无条件 `UPDATE`，可能让两个请求均成功，最终由后写者静默覆盖。

修复规格：

- 认领必须使用 `UPDATE ... WHERE id = ? AND status = 'OPEN'`。
- 排期必须使用 `UPDATE ... WHERE id = ? AND status = 'CLAIMED'`。
- 归档必须使用 `UPDATE ... WHERE id = ? AND status = 'SCHEDULED'`。
- 以 SQLite `changes` 作为唯一成功依据。
- `changes = 0` 时复查 ID：不存在返回 `404`，存在但状态变化返回 `409`。
- 不能仅依赖单进程同步执行或普通 deferred transaction。

验收：

- 两个独立应用实例连接同一临时数据库，并发认领同一议题时，恰好一个 `200`、一个 `409`。
- 最终 `presenter` 等于唯一成功响应中的认领人。
- 排期和归档继续遵守状态机，现有生命周期测试全部通过。

### BUG-CONC-003 PATCH 全行丢失更新

复现：PATCH 先读取 `CLAIMED` 整行快照并暂停；另一实例完成排期；PATCH 随后把旧快照中的空排期字段与标题一起全量写回，最终记录状态为 `SCHEDULED`，但 `scheduled_at/duration/room` 为空。

修复规格：

- PATCH 只生成请求实际提交字段的白名单 `SET` 列，不得回写未提交字段。
- `updated_at` 始终更新。
- 状态权限仍按读取时状态校验；并发生命周期动作更新的其他列必须保留。
- 更新期间记录被删除时返回 `404`。

验收：

- 两个共享数据库的应用实例通过测试钩子形成可控交错：PATCH 标题读取后暂停，另一实例完成排期，再恢复 PATCH。
- 两个请求均成功时，最终标题为新标题，状态为 `SCHEDULED`，且分享人、时间、时长、地点全部保留。
- 同理，普通字段编辑不得清除归档摘要、资料或归档时间。
- 现有全部单元/API/E2E 继续通过。

实现与验证：

- PATCH 已改为根据请求字段生成白名单动态 `SET`，不再合并并回写整行快照。
- 新增测试钩子形成确定性交错：编辑读取后暂停 → 第二实例排期 → 恢复编辑。
- 最终新标题与 `SCHEDULED` 状态并存，分享人、时间、50 分钟时长和地点全部保留。
- 12 项单元/API 测试、桌面 5 项 E2E、移动 3 项 E2E、生产构建和 0 漏洞审计通过。
- 状态：Accepted；实现提交 `33baec0`。

### BUG-CONC-004 排序陈旧写与 UI/DB 分叉

复现 A（多客户端）：两个客户端都读取版本 `r` 和顺序 `[1,2,3]`；甲提交 `[2,1,3]` 成功，乙仍基于 `r` 提交 `[1,3,2]` 也成功，静默覆盖甲。

复现 B（单页面乱序）：R1 上移请求被延迟，R2 后续移动先成功，R1 最后成功或失败；UI 使用 R2 的乐观顺序，数据库可能保留 R1，或 R1 的失败回滚覆盖 R2，刷新时发生跳变。

后端修复规格：

- 新增单例顺序元数据 `manual_order_version`，旧库从 `0` 开始。
- `GET /api/topics` 保持数组响应，并通过 `X-Order-Version` 返回当前非负整数版本。
- `POST /api/topics/reorder` 必须提交 `baseVersion`。
- 在同一个 `BEGIN IMMEDIATE` 事务中完成：读取/校验版本、校验完整 ID 集、写入连续唯一 position、版本 `+1`。
- 陈旧版本返回 `409`，并在响应头返回当前版本；不得修改任何 position。
- 创建在立即写事务中分配末尾位置并推进版本，防止并发重复 position。
- 删除在立即写事务中删除、压实连续 position 并推进版本。
- 位置重排采用安全的两阶段临时值，允许数据库建立唯一索引。

前端修复规格：

- 保存 `X-Order-Version`，重排携带当前 `baseVersion`。
- 使用同步锁保证任一时刻最多一个 reorder 在途；保存期间拖动、上移和下移全部禁用。
- 成功后使用响应头的新版本继续后续操作。
- 409 或其他失败均先恢复操作前快照，再拉取服务端权威手动顺序和版本；明确提示冲突/失败。
- `aria-live` 宣告保存中、成功位置或已同步最新顺序。

验收：

- 两个共享数据库的应用实例基于同一版本提交不同顺序，恰好一个 `204`、一个 `409`；最终顺序等于成功者，position 为 `1..N`。
- 快照后发生创建或删除，旧 reorder 返回 `409`。
- 浏览器延迟首个请求时，全部排序控件禁用，强制第二次操作不得发出第二个请求。
- 请求完成后 UI、`GET` 和刷新结果一致；失败路径重新同步权威顺序。
- 全部既有测试继续通过。

### BUG-DATA-005 演示数据在清空后复活

根因：生产默认启用 seed，而初始化仅用 `COUNT(topics) === 0` 判断；用户合法删除最后一条议题后，下次启动会被误判为全新数据库。

修复规格：

- 新增持久化 `app_state(key, value)`，使用 `sample_data_initialized` 一次性标记。
- 标记不存在时才执行初始化决策：
  - `seed=true` 且业务表为空：插入演示数据；
  - `seed=false` 或已有业务数据：不插入；
  - 无论是否插入，均写入初始化标记。
- 标记存在时不得因业务表为空再次插入样例。
- 旧数据库升级时若已有业务数据，仅补标记，不改数据。

验收：

- 同一临时数据库首次 `seed=true` 得到 4 条样例；通过 API 删除全部，关闭并按相同配置重开后仍为 `[]`。
- 全新数据库首次 `seed=false` 保持为空；关闭后以 `seed=true` 重开仍为空。
- 旧数据库已有数据、没有标记时升级只补标记，不新增样例。
- 全部现有测试继续通过。

状态：Accepted。

实现与验证：

- 新增 `app_state` 与 `sample_data_initialized` 一次性标记。
- 首次启动无论 seed 开关或是否已有数据，都会固化初始化决策；后续不再用业务表为空推断。
- 15 项测试通过，包含 seed 后清空重启仍为空、首次禁用后重启仍为空、旧库无损升级。
- 桌面 6 项、移动 4 项 E2E、生产构建和 0 漏洞审计通过。
- 实现提交：`4f6cdf1`。

选择理由：两个缺陷发生在同一条“读取排序快照 → 编辑 → CAS 保存”链路。只修服务端仍会允许浏览器把其他排序模式的列表作为手动顺序提交；只修前端仍会接收服务端混合快照并绕过版本冲突。因此本轮以“排序读取快照端到端一致性”为单一质量目标，同时封闭服务端快照边界和客户端请求来源边界。

### BUG-CONC-006 列表与顺序版本的非原子快照

复现：实例甲的 `GET /api/topics` 先读取旧顺序 `[1,2,3]` 后暂停；实例乙完成重排并把版本从 `r` 推进至 `r+1`；实例甲再读取版本，返回“旧列表 + 新版本”。客户端基于这组混合数据重排时能通过 CAS，静默覆盖实例乙的结果。

服务端修复规格：

- `GET /api/topics` 的议题行与 `X-Order-Version` 必须来自同一个 SQLite 只读事务快照。
- 快照读取不能阻止另一数据库连接在 WAL 模式下完成写入。
- 查询失败时必须回滚已开启的读取事务，连接不得残留事务状态。
- 所有排序和状态筛选模式都遵守同一快照规则。

服务端验收：

- 两个应用实例共享数据库；实例甲读取 rows 后由测试钩子暂停，实例乙完成重排并推进版本，再恢复实例甲。
- 实例甲只能返回“旧列表 + 旧版本”或“新列表 + 新版本”，不得返回混合快照。
- 若实例甲拿到旧快照，随后以该版本重排必须返回 `409`，且不得覆盖实例乙的权威顺序。
- 创建或删除与 GET 交错时同样遵守快照一致性；既有 CAS 回归全部通过。

### BUG-UI-007 过期排序请求污染当前手动列表

复现：手动顺序为 `[A,B,C]`、最新创建排序为 `[C,B,A]`。延迟 `sort=newest` 响应，快速切换“最新创建 → 手动排序”；新的 manual 请求先完成，旧 newest 请求后完成。旧实现仍回写旧响应，导致选择框显示“手动排序”但列表为 `[C,B,A]`；一次上移/下移即可把错误来源以合法版本永久保存。

前端修复规格：

- 每次列表加载分配单调递增请求序号；只有最新请求可以原子提交 `topics + orderVersion + loadedSort`。
- 过期请求不得更新议题、版本、加载态或错误态；统计响应可以独立更新，不受议题排序请求竞争影响。

### BUG-MIG-008 重复位置旧库无法升级

复现：构造一个已有 `position` 字段但尚无唯一索引的历史数据库，至少两条议题的非零 `position` 相同；调用 `buildApp()` 时，旧实现执行 `CREATE UNIQUE INDEX idx_topics_position` 并抛出 `UNIQUE constraint failed: topics.position`。

迁移规格：

- 创建唯一索引前检查 `idx_topics_position` 是否已经是唯一索引。
- 唯一索引尚未建立时，在同一个立即写事务中按 `(position ASC, id ASC)` 读取全部议题，将位置稳定归一化为连续 `1..N`，随后创建唯一索引。
- 旧库缺少 `position` 字段时先添加字段，再走相同归一化流程；不能依赖一次性的 `position = id` 更新。
- 若存在同名非唯一索引，迁移应替换为唯一索引，不能因 `IF NOT EXISTS` 静默失去约束。
- 迁移不得修改标题、简介、人员、标签、状态、排期、归档或审计时间等业务字段。
- 迁移可重复执行；第二次及以后启动不得改变已归一化顺序。

验收：

- 自动化构造位置为 `[2,1,1]` 且含不同业务字段的旧库；首次启动成功。
- 迁移后按旧 `(position,id)` 相对顺序返回，位置严格为 `1..N`，所有业务字段逐项不变。
