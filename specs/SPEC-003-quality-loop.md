# SPEC-003：独立 Agent 质量收敛循环

- 状态：`Implementing`
- 创建：2026-09-01
- 最后更新：2026-09-01

## 1. 目标

通过彼此独立的产品、后端和体验审查，持续发现一个最值得实现的需求或最有必要修复的 BUG；每轮只引入一个主要变量，完成规格、开发和验证后再进入下一轮，直到项目质量收敛。

## 2. 每轮流程

1. 启动必要数量的独立 agent，默认覆盖产品价值、数据正确性、交互/可访问性。
2. 每个 agent 只推举 1 项，必须包含证据、用户影响和验收标准，不直接改代码。
3. 主 agent 按以下顺序选择本轮唯一最高优先级项：
   - P0 数据丢失、安全或服务不可用
   - P1 核心流程错误、并发一致性、明确需求不可用
   - P2 显著提升完成率或可访问性的功能
   - P3 纯视觉或便利性优化
4. **先更新对应规格**，写入复现路径/需求和验收标准。
5. 开发、添加回归测试、完成构建和浏览器验证。
6. 将验证证据回写规格，然后开始下一轮独立审查。

## 3. 停止条件

同时满足以下条件时终止循环：

- 连续一轮所有独立审查均没有发现新的 P0/P1。
- 没有未实现的用户明确需求。
- 当前规格的自动化和浏览器验收全部通过。
- 依赖审计没有 moderate 及以上漏洞。
- 剩余建议均为低价值偏好、需要用户业务决策，或明确超出当前产品边界。

终止时必须列出未实现的低优先级建议及不实施原因，不能默默忽略。

### BUG-CONC-001 生命周期转换竞态

复现条件：两个连接同一 SQLite 文件的服务实例，同时读取同一 `OPEN` 议题并提交不同认领人。旧实现先 `SELECT` 校验、再按 `id` 无条件 `UPDATE`，可能让两个请求均成功，最终由后写者静默覆盖。

修复规格：

- 认领必须使用 `UPDATE ... WHERE id = ? AND status = 'OPEN'`。
- 排期必须使用 `UPDATE ... WHERE id = ? AND status = 'CLAIMED'`。
- 归档必须使用 `UPDATE ... WHERE id = ? AND status = 'SCHEDULED'`。
- 以 SQLite `changes` 作为唯一成功依据。
- `changes = 0` 时复查 ID：不存在返回 `404`，存在但状态变化返回 `409`。
- 不能仅依赖单进程同步执行或普通 deferred transaction。

验收：

- 两个独立应用实例连接同一临时数据库，并发认领同一议题时，恰好一个 `200`、一个 `409`。
- 最终 `presenter` 等于唯一成功响应中的认领人。
- 排期和归档继续遵守状态机，现有生命周期测试全部通过。

### BUG-CONC-003 PATCH 全行丢失更新

复现：PATCH 先读取 `CLAIMED` 整行快照并暂停；另一实例完成排期；PATCH 随后把旧快照中的空排期字段与标题一起全量写回，最终记录状态为 `SCHEDULED`，但 `scheduled_at/duration/room` 为空。

修复规格：

- PATCH 只生成请求实际提交字段的白名单 `SET` 列，不得回写未提交字段。
- `updated_at` 始终更新。
- 状态权限仍按读取时状态校验；并发生命周期动作更新的其他列必须保留。
- 更新期间记录被删除时返回 `404`。

验收：

- 两个共享数据库的应用实例通过测试钩子形成可控交错：PATCH 标题读取后暂停，另一实例完成排期，再恢复 PATCH。
- 两个请求均成功时，最终标题为新标题，状态为 `SCHEDULED`，且分享人、时间、时长、地点全部保留。
- 同理，普通字段编辑不得清除归档摘要、资料或归档时间。
- 现有全部单元/API/E2E 继续通过。

实现与验证：

- PATCH 已改为根据请求字段生成白名单动态 `SET`，不再合并并回写整行快照。
- 新增测试钩子形成确定性交错：编辑读取后暂停 → 第二实例排期 → 恢复编辑。
- 最终新标题与 `SCHEDULED` 状态并存，分享人、时间、50 分钟时长和地点全部保留。
- 12 项单元/API 测试、桌面 5 项 E2E、移动 3 项 E2E、生产构建和 0 漏洞审计通过。
- 状态：Accepted；实现提交 `33baec0`。

### BUG-CONC-004 排序陈旧写与 UI/DB 分叉

复现 A（多客户端）：两个客户端都读取版本 `r` 和顺序 `[1,2,3]`；甲提交 `[2,1,3]` 成功，乙仍基于 `r` 提交 `[1,3,2]` 也成功，静默覆盖甲。

复现 B（单页面乱序）：R1 上移请求被延迟，R2 后续移动先成功，R1 最后成功或失败；UI 使用 R2 的乐观顺序，数据库可能保留 R1，或 R1 的失败回滚覆盖 R2，刷新时发生跳变。

后端修复规格：

- 新增单例顺序元数据 `manual_order_version`，旧库从 `0` 开始。
- `GET /api/topics` 保持数组响应，并通过 `X-Order-Version` 返回当前非负整数版本。
- `POST /api/topics/reorder` 必须提交 `baseVersion`。
- 在同一个 `BEGIN IMMEDIATE` 事务中完成：读取/校验版本、校验完整 ID 集、写入连续唯一 position、版本 `+1`。
- 陈旧版本返回 `409`，并在响应头返回当前版本；不得修改任何 position。
- 创建在立即写事务中分配末尾位置并推进版本，防止并发重复 position。
- 删除在立即写事务中删除、压实连续 position 并推进版本。
- 位置重排采用安全的两阶段临时值，允许数据库建立唯一索引。

前端修复规格：

- 保存 `X-Order-Version`，重排携带当前 `baseVersion`。
- 使用同步锁保证任一时刻最多一个 reorder 在途；保存期间拖动、上移和下移全部禁用。
- 成功后使用响应头的新版本继续后续操作。
- 409 或其他失败均先恢复操作前快照，再拉取服务端权威手动顺序和版本；明确提示冲突/失败。
- `aria-live` 宣告保存中、成功位置或已同步最新顺序。

验收：

- 两个共享数据库的应用实例基于同一版本提交不同顺序，恰好一个 `204`、一个 `409`；最终顺序等于成功者，position 为 `1..N`。
- 快照后发生创建或删除，旧 reorder 返回 `409`。
- 浏览器延迟首个请求时，全部排序控件禁用，强制第二次操作不得发出第二个请求。
- 请求完成后 UI、`GET` 和刷新结果一致；失败路径重新同步权威顺序。
- 全部既有测试继续通过。

### BUG-DATA-005 演示数据在清空后复活

根因：生产默认启用 seed，而初始化仅用 `COUNT(topics) === 0` 判断；用户合法删除最后一条议题后，下次启动会被误判为全新数据库。

修复规格：

- 新增持久化 `app_state(key, value)`，使用 `sample_data_initialized` 一次性标记。
- 标记不存在时才执行初始化决策：
  - `seed=true` 且业务表为空：插入演示数据；
  - `seed=false` 或已有业务数据：不插入；
  - 无论是否插入，均写入初始化标记。
- 标记存在时不得因业务表为空再次插入样例。
- 旧数据库升级时若已有业务数据，仅补标记，不改数据。

验收：

- 同一临时数据库首次 `seed=true` 得到 4 条样例；通过 API 删除全部，关闭并按相同配置重开后仍为 `[]`。
- 全新数据库首次 `seed=false` 保持为空；关闭后以 `seed=true` 重开仍为空。
- 旧数据库已有数据、没有标记时升级只补标记，不新增样例。
- 全部现有测试继续通过。

状态：Accepted。

实现与验证：

- 新增 `app_state` 与 `sample_data_initialized` 一次性标记。
- 首次启动无论 seed 开关或是否已有数据，都会固化初始化决策；后续不再用业务表为空推断。
- 15 项测试通过，包含 seed 后清空重启仍为空、首次禁用后重启仍为空、旧库无损升级。
- 桌面 6 项、移动 4 项 E2E、生产构建和 0 漏洞审计通过。
- 实现提交：`4f6cdf1`。
