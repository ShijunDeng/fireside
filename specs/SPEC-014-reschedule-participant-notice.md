# SPEC-014：有报名活动的改期通知确认

- 状态：`Accepted`
- 创建：2026-09-02
- 最后更新：2026-09-02

## 1. 用户问题

未来活动已有报名伙伴时，协调者可以直接修改时间、时长、地点或线上入口。服务端按正确不变量保留报名名单，但页面既不显示受影响人数，也不说明系统不会自动通知；参与者仍显示“已报名”却可能完全不知道安排变化，造成实际错过活动。

该问题违反 SPEC-004 已接受规则：“普通改期保留参与名单，并提示系统暂不自动通知参与者”。

## 2. 业务规则

- 只在 `SCHEDULED + UPCOMING + participantCount > 0`，且本次编辑修改以下任一活动安排字段时触发二次确认：`scheduledAt`、`duration`、`room`、`meetingUrl`。
- 确认页显示受影响报名人数和每项旧值/新值；线上入口只显示“未设置 / 已设置 / 已变更”，不得回显 URL 或凭证。
- 必须明确提示：“系统不会自动通知报名伙伴，请确认已通过其他方式通知。”
- 取消确认不得发送 PATCH，并回到保留全部草稿的编辑表单。
- 确认后提交原快照 payload，完整保留报名名单；成功提示包含人数和另行通知责任。
- 纯标题/简介/发起人/分享人/标签修改，或零报名活动，不增加确认步骤。
- 确认期间若 revision 变化，原确认立即失效；不得自动重放。读取最新版后回到编辑冲突流程，要求协调者基于最新版重新检查并再次确认。
- 确认提交若收到 `400 / 413 / 415 / 500` 可重试错误，保留当前确认层、报名人数、变更对照和 pending payload；错误在确认层内可见且获得焦点，不得误报已保存或自动重试。

## 3. 交互与可访问性

- 二次确认仍由同一顶层 dialog 拥有，不能创建叠层或破坏滚动锁。
- 进入确认后焦点落到确认标题；返回编辑后焦点回“保存修改”。
- 确认区按“受影响人数 → 变更对照 → 通知说明 → 返回修改 / 确认保存”排序。
- 桌面、平板和 Pixel 7 不横向溢出；两个动作在移动端均至少 44px。

## 4. 验收

1. 创建未来活动并报名 1 人；修改时间，提交后先看到旧/新时间、1 人和不自动通知说明，网络中没有 PATCH。
2. 返回修改后字段草稿完整保留；再次保存仍进入确认。
3. 确认后 PATCH 一次，排期更新；参与名单、列表/月历/周历/详情人数都仍为 1，成功反馈明确需另行通知。
4. 修改时长、地点和线上入口均触发；入口对照不含 URL/查询参数/凭证。
5. 纯内容修改与零报名活动直接保存，不触发确认。
6. 确认期间制造远端 revision 变化，确认返回 412；页面不得自动重试，旧确认消失，草稿保留并要求基于最新版重新保存、重新确认。
7. 桌面 Chrome 与 Pixel 7 覆盖取消、确认、冲突、焦点恢复、44px 和无横向溢出。

## 5. 实现与验证

- 编辑器只在未来、已有报名且活动安排字段发生变化时切换到同一 dialog 内的确认页；确认页显示人数、旧/新值和明确的线下通知责任，会议入口仅显示脱敏状态。
- “返回修改”不发请求并保留表单；成功保存保留报名名单，反馈包含受影响人数。确认遇到 412 后原确认失效，协调者必须基于最新版重新保存并再次确认。
- 冲突恢复采用三方合并：服务器更新的未触碰字段进入新草稿，用户实际修改字段继续保留，避免重试覆盖其他协作者的新内容。
- 移动端弹窗初始焦点改在 layout 阶段一次性完成，消除延迟焦点抢占正在编辑字段的竞争；确认和返回焦点、44px 动作与无横向溢出均纳入回归。
- `npm run check`：145 项单元/API/运维测试、类型检查和生产构建通过；`npx playwright test --retries=0`：桌面 Chrome 与 Pixel 7 共 61 通过、3 项按设备职责跳过。
- SPEC-013 回归补齐可重试请求错误分支：桌面 400、Pixel 7 413 均保留确认层并聚焦可见错误，全量 154 项 `check` 与 80 项无重试跨端 E2E 通过。
