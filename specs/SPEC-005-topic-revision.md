# SPEC-005：议题聚合版本与陈旧操作保护

- 状态：`Accepted`
- 创建：2026-09-02
- 关联：SPEC-003 第 9 轮、SPEC-002 CRUD、SPEC-004 协作流程

## 1. 问题与目标

当前多人从同一议题快照操作时，后提交的全量编辑会静默覆盖先提交内容；删除确认打开后，其他人新增的排期或报名也会被旧 DELETE 永久级联删除。现有状态 CAS 和全局排序版本都不能识别同状态内容变化或参与集合变化。

本规格为 Topic 业务聚合增加单调 revision，以 HTTP 前置条件保护内容、生命周期和删除；失败必须可恢复、不得自动重放。

## 2. 聚合版本规则

`topics` 新增 `revision INTEGER NOT NULL DEFAULT 1 CHECK(revision >= 1)`：

| 操作 | revision 结果 |
| --- | --- |
| 创建议题 | 初始为 1 |
| PATCH 内容/排期/归档字段 | 成功后 +1 |
| 认领、退出认领、排期、取消排期、归档、撤销归档 | 成功后 +1 |
| 成功报名、成功取消报名 | 父议题 +1 |
| 重复报名、无效取消、校验/状态/版本失败 | 不变 |
| 取消排期并清空全部报名 | 整个事务只 +1 |
| 手动排序 | 不变，继续只推进 `orderVersion` |
| 删除 | 被删记录无需递增；其余议题 revision 不变 |

报名/取消报名本身不要求调用者提供 revision，避免正常并发报名互相阻塞；参与记录写入/删除与父议题 revision 递增必须处于同一个立即写事务。

排序只更新 position，不再修改 `updated_at`；topic revision 与 orderVersion 两个并发域严格隔离。

## 3. `If-Match` API 契约

以下已有议题命令必须携带打开页面或弹窗时看到的强实体标签：`If-Match: "<正整数 revision>"`：

- `PATCH /api/topics/:id`
- `DELETE /api/topics/:id`
- `POST /api/topics/:id/claim|release|schedule|unschedule|archive|unarchive`

创建、reorder、报名、取消报名不要求该头。全部公开 Topic 返回（列表、单项、统计 nextTopic、mutation 响应）包含 revision。

错误优先级与稳定错误码：

1. 写口令不正确仍先返回 `401 ACCESS_REQUIRED`。
2. 缺少 `If-Match`：`428 TOPIC_REVISION_REQUIRED`。
3. 非法格式、弱标签、通配符、多标签或非正整数：`400 INVALID_TOPIC_REVISION`。
4. ID 不存在：`404 TOPIC_NOT_FOUND`。
5. ID 存在但 revision 不同：`412 TOPIC_REVISION_CONFLICT`，不得写入任何字段。
6. revision 相同但状态不允许：`409 TOPIC_STATE_CONFLICT`。

内容与生命周期 SQL 必须在同一语句匹配 revision、递增 revision 并通过 `RETURNING` 取得响应行，避免成功写入后的独立 SELECT 竞态。状态相关 PATCH 同时匹配读取状态；版本与状态同时变化时优先报告 revision 冲突。

## 4. 迁移

- 启动时检查 `topics.revision`，旧库缺列时执行幂等迁移，已有数据统一从 1 开始。
- 迁移不得改变任何内容、状态、排期、报名、position、时间或排序版本。
- 重复启动不得重复改值或失败。

## 5. 浏览器交互

- API 客户端对上述命令发送 Topic 当前 revision。
- 编辑表单只提交相对打开快照真正变化的字段：文本按 trim 后比较，标签按解析数组比较，数字按数值比较，日期按表单分钟精度比较；没有变化时不发送请求并提示。
- 编辑收到 `412 TOPIC_REVISION_CONFLICT` 时保持弹窗与全部输入，后台只读取最新 Topic；若状态未变，显示 `role=alert` 冲突说明并提供“基于最新版再次保存”，由用户显式点击后只重交 dirty 字段。不得自动重放。
- 用户也可以放弃冲突草稿：关闭按钮、Escape 和点击遮罩必须复用同一恢复动作，关闭弹窗且不再发送 PATCH，并立即把列表卡片同步为后台已读取的最新版；不得继续显示旧标题使用户误以为远端更新丢失。
- 若最新状态已变化，沿用状态冲突恢复：关闭陈旧表单、同步权威状态。
- 删除及无草稿生命周期操作收到 412 时关闭旧确认、刷新并提示“议题已被其他协作者更新，本次操作未执行”；用户必须重新打开基于最新 revision 的确认框。
- 401 继续遵守 SPEC-004：保留底层表单，解锁后不自动重放。

## 6. 验收矩阵

1. 新建 revision=1；每条内容/正反生命周期成功后精确 +1，失败不变。
2. 成功报名 +1、重复报名不变、成功取消 +1、缺失取消不变。
3. 同 revision 双编辑：首个成功，后者 412，首个结果不被覆盖；后者读取最新版并显式重交 dirty 字段后，两人的非冲突修改并存。
4. 删除确认后发生 PATCH、排期或报名：陈旧 DELETE 均 412，议题、排期、参与者和 orderVersion 保持；最新 revision 再次明确确认才 204。
5. 取消排期确认后发生报名：陈旧 unschedule 412 且报名保留；基于最新版取消时排期与报名原子清除、revision 只 +1。
6. reorder 后 topic revision 不变而 orderVersion +1，原 revision 的内容命令仍可执行；删除只推进 orderVersion，不改变其余议题 revision。
7. 无口令且无 If-Match 返回 401；正确口令但缺头返回 428；非法格式矩阵返回 400。
8. 双实例确定性交错覆盖 PATCH、DELETE 与状态 CAS；mutation 响应不能出现写成功后被并发删除导致的 500。
9. 桌面 Chrome 与 Pixel 7 均覆盖编辑草稿保留/显式重交、关闭后放弃草稿并即时同步远端卡片、删除冲突拒删/重新确认，以及正常无冲突旅程。
10. 旧库迁移、重复启动、全部既有 API/E2E、生产构建与漏洞审计通过。

## 7. 非目标

- 本轮不实现完整历史版本浏览、回收站、审计日志或多人实时协同编辑。
- 本轮不让排序推进 Topic revision。
- 本轮不要求报名者处理 If-Match。

## 8. 浏览器确定性并发场景

桌面 Chrome 与 Pixel 7 使用相同的确定性交错，不依赖请求碰撞概率：

1. 页面从 revision `r` 打开编辑框并修改简介；测试 API 使用 `If-Match: "r"` 修改标题到 `r+1`；页面首次保存必须收到 412，编辑框、简介草稿和冲突提示均保留。用户点击“基于最新版再次保存”后，只重交 dirty 简介，最终同时保留远端标题和本地简介。
2. 同样制造 412 后，用户点击关闭按钮放弃草稿；弹窗关闭、本地简介不进入服务端，列表无需整页刷新即可显示远端标题与原简介。关闭按钮是该语义的必测入口；Escape 与遮罩复用同一产品代码路径，不得形成另一套丢弃/同步行为。
3. 页面从已排期 revision `r` 打开删除确认；测试 API 成功报名并把父议题推进到 `r+1`；页面确认删除必须收到 412 并关闭旧确认。刷新后议题仍存在、参与人数为 1，受保护参与名单仍能看到该报名人；测试清理必须重新读取最新 revision 后才能删除。

E2E 中所有直接生命周期与删除调用也必须携带所读快照的 `If-Match`；清理逻辑不得通过省略前置条件绕过生产契约。

验证记录：显式重试、放弃草稿和陈旧删除三条并发恢复场景在桌面 Chrome 与 Pixel 7 分项运行 6/6 通过，其中关闭放弃路径定向 2/2；完整跨端套件 34 项通过，另 2 项按设备设计跳过。既有 E2E 的直接排期、归档、取消排期和删除调用均已按 revision 快照携带 `If-Match`。40 项单元/API/安全/并发测试、TypeScript、生产构建、差异检查和 0 漏洞审计全部通过。
