# SPEC-016：UTF-8 围炉口令与六字符生产门槛

- 状态：`Accepted`
- 创建：2026-09-02
- 最后更新：2026-09-02
- 关联：SPEC-004 FR-ACCESS-001、SPEC-009 FR-AUTH-001/010/011/012/014

## 1. 用户目标与已复现阻断

围炉口令改为至少 6 个字符，当前生产配置改为用户最后指定的 8 字符值。生产仍必须显式配置口令，不能因环境变量缺失而退回匿名可写。

现有页面把口令原文写入 `X-Fireside-Write-Key`。浏览器 Fetch 的请求头值使用 ByteString；输入中文会在请求发出前抛出异常，因而只修改 `/etc/fireside.env` 会让所有网页协作者无法解锁。

## 2. 生产口令规则

- `NODE_ENV=production` 时必须显式设置 `FIRESIDE_WRITE_KEY`，且值与自身 `trim()` 完全相同。
- 长度按 Unicode code point 计算，为 `6..256`；emoji 计一个 code point。少于 6、超过 256、空值、缺失或首尾空白均在监听端口和打开数据库前拒绝。
- 按用户“至少 6 个字符即可”的要求，不再额外拒绝占位词或同一字符重复；最大 256 保留为资源边界，不声称衡量真实熵。
- 当前生产值只存放在 Git 外的 `/etc/fireside.env`，文件保持 `root:root 0600`；源码不得在变量缺失时内置回退口令。
- 口令轮换继续立即使旧协作会话失效；原始值、等价编码、摘要和完整会话令牌不得进入日志、URL或错误响应。

## 3. 浏览器传输协议

- 页面将用户输入按 UTF-8 编码，再用无 padding 的 canonical base64url 表示，值放入 `X-Fireside-Write-Key`，并以 `X-Fireside-Write-Key-Encoding: base64url-utf8-v1` 显式标记版本。
- 服务端只对 `/api/access/verify` 读取这两个头：严格校验唯一 encoding 值、base64url 字符集、canonical 重编码、UTF-8 fatal 解码和最多 1024 UTF-8 bytes；任何失败都作为一次错误候选进入既有限流，稳定返回 `401` 或 `429`，不得抛出 `500`。
- 为平滑迁移，缺少 encoding 头时暂时把 `X-Fireside-Write-Key` 按旧 ASCII 原文处理；含非 ASCII 的无版本头和未知 encoding 拒绝。前端从本轮起只发送版本化格式。
- 编码不是加密；Pino 对整个请求头继续脱敏。业务写和敏感读取仍只接受 `X-Fireside-Session`，不得恢复原始口令旁路。
- 限流顺序、来源桶、全局桶、阻断期和 8 小时会话语义保持 SPEC-009 不变。

## 4. 页面体验

- 解锁表单直接接受中文、英文、emoji 与混合口令；输入中文不得出现浏览器技术错误。
- 错误口令继续显示“围炉口令不正确”，429 继续显示等待时间；两者都清空原始输入但保留底层业务草稿。
- 页面不展示、预填或存储生产口令；成功后当前标签页只保存短期会话令牌。
- 共享口令只定位为小团队公开站点的防误操作边界；当前 HTTP/80 不提供传输保密性，若承载更敏感数据仍需 HTTPS 与个人身份体系。

## 5. 验收

1. 生产门禁覆盖 5/6/8/256/257 个 code point、emoji、缺失、空值和首尾空白；6 字及同字符重复 6 次通过，失败消息不回显值。
2. 编解码覆盖中文、ASCII、emoji、canonical base64url；非法字符、padding、非 canonical、非法 UTF-8、超长、重复或未知 encoding 稳定失败且不泄密。
3. API 使用版本化中文候选签发会话；错误编码按失败计桶，阻断期正确中文仍为 429；旧 ASCII 头兼容，业务路由继续拒绝原始口令。
4. 桌面 Chrome 与 Pixel 7 均用中文生产等价测试口令完成解锁和至少一次真实业务写；捕获请求证明验证值只有 ASCII 且 encoding 为 `base64url-utf8-v1`，后续业务请求只有会话头。
5. 口令轮换后旧会话失效，新会话生效；日志、拒绝响应和工作树均不含生产口令或测试秘密。
6. 更新 README、SPEC-004、SPEC-009 和迭代记录；全量单元/API/E2E、TypeScript、生产构建与生产 80 端口验证通过。

## 6. 实现与验证证据

- 新前端统一发送 canonical UTF-8 base64url 值和 `base64url-utf8-v1` 标记；服务端执行字符集、canonical、fatal UTF-8 与 1024 bytes 上限校验，非法编码按普通失败进入原有限流。无 encoding 的旧 ASCII 验证继续兼容，业务路由仍只接受短期会话。
- 生产启动规则为显式配置、无首尾空白、6..256 Unicode code point；6 个重复字符与旧占位词也按用户规则接受，缺失、5、257 或首尾空白继续在监听和数据库前失败关闭。
- 页面支持中文输入并在少于 6 字符时本地明确反馈；不预填、不保存原始口令，成功后仅保存 8 小时会话令牌。
- `npm run check` 的 146 项单元/API/安全/发布测试、TypeScript 与生产构建全部通过；Playwright 使用 7 字中文测试口令跑完桌面 Chrome 与 Pixel 7 全业务，66 项通过、4 项按设备职责跳过，`--retries=0`。
- 生产验收待提交部署后回写 commit、80 端口和最终口令轮换证据。
