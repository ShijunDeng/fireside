# SPEC-015：任务导航落点与合理排版

- 状态：`Accepted`
- 创建：2026-09-02
- 最后更新：2026-09-02

## 1. 用户问题

桌面吸顶导航、移动菜单和页脚都提供“议题广场 / 本周活动 / 待归档 / 往期回顾 / 如何参与”入口，但当前滚动目标是区块内的标题，而 `scroll-margin-top` 写在父区块。导航完成后标题顶部落在约 `0px`，被 64–76px 的吸顶栏完全遮住。

“如何参与”还没有可编程焦点和当前目的地状态；移动菜单关闭时的焦点恢复会与页面导航竞争，最终可能回到已经消失的菜单触发按钮。用户看见入口却不能清楚确认“我到了哪里”，属于页面功能与合理排版同时不完整。

## 2. 导航模型

- 五个任务目的地使用同一组语义键：`topics / week / ended / archived / how`；桌面导航和移动菜单不得维护两套状态。
- `topics / week / ended / archived` 的当前态由实际工作区筛选与视图派生；`how` 由最近一次显式导航到流程区激活。
- 任何进入议题工作区的快捷动作都清除 `how` 当前态；不存在精确对应顶栏任务的搜索或组合筛选时，可以没有 `aria-current`，不得标错。
- 桌面、移动菜单和页脚入口必须调用同一个导航命令；移动菜单选择后由导航命令关闭菜单，不能让菜单关闭与目的地聚焦各自抢焦点。

## 3. 排版与焦点规则

- 五个入口完成后，目标标题顶部必须位于实际吸顶栏底部以下至少 `8px`；标题不能被遮挡，也不能只依赖用户继续滚动修正。
- 议题类目的地统一聚焦“炉边正在发生什么”；如何参与聚焦“从一点好奇，到一束火光”。两个标题都必须可编程聚焦但不进入普通 Tab 顺序。
- 滚动与焦点在视图状态提交、移动菜单卸载和其焦点恢复之后执行；最终焦点必须稳定落在目的标题。
- 同一时刻最多一个对应入口具有 `aria-current="page"`。重新打开移动菜单后，当前标记必须与刚到达的目的地一致。
- 尊重 `prefers-reduced-motion`；不得引入页面横向溢出或改变现有 44px 触控基线。

## 4. 验收

1. 在 1440×1000 逐一点击桌面五个入口：目标标题聚焦、顶部在 header 底部 + 8px 之后，且只有对应按钮为当前项。
2. 在 820×1180 和 Pixel 7 从移动菜单逐一进入五个目的地：菜单关闭后最终焦点位于标题；重新打开菜单时只有对应项为当前项。
3. 从页脚进入议题、活动、往期和如何参与，验证相同的落点、焦点与当前态。
4. 从“如何参与”的任一步进入议题工作区后，`how` 当前态清除并切换到与实际工作区匹配的任务态或无当前态。
5. 三种视口均无横向溢出；既有导航、日历、弹窗焦点和业务 E2E 全部继续通过。

## 5. 实现与验证

- 桌面导航、移动菜单和页脚统一调用同一目的地命令；移动菜单不再另行排队关闭与滚动，目的地焦点在菜单卸载和焦点恢复后以可撤销的双帧任务提交。
- `topics / week / ended / archived / how` 使用同一当前态模型；搜索、筛选、视图切换和流程快捷动作进入工作区时清除 `how`，避免把历史落点误标为当前页面。
- 两个目标标题均具有可编程焦点；桌面/平板使用 `88px`、手机使用 `76px` 的标题滚动边距，实测三种视口均满足吸顶栏后至少 `8px` 可见间距且无横向溢出。
- 滚动行为遵循 `prefers-reduced-motion`：减少动态效果时使用即时滚动，其余场景保留平滑过渡。
- 验证证据：`npm run check` 的 145 项单元/API/运维测试、TypeScript 与生产构建全部通过；Playwright 在桌面 Chrome 与 Pixel 7 共 66 项通过、4 项按设备职责跳过，且使用 `--retries=0`。
