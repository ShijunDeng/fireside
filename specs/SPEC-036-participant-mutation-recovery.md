# SPEC-036：报名写入成功后的名单一致性与恢复

- 状态：`Accepted`
- 创建：2026-09-02
- 优先级：P2
- 关联：SPEC-004、SPEC-005、SPEC-011、SPEC-023、SPEC-030

## 1. 已复现

未来活动的报名 `POST` 已返回 201，或取消报名 `DELETE` 已返回 204，若紧随的 `GET /participants` 返回 503，弹窗曾显示写入前的相反名单：成功报名的人不可见，成功取消的人仍可再次点取消。第 30 轮继续复现两个相邻断点：写入后底层 `GET /topics` 503 会用全局错误替换整张广场；首次 `GET /participants` 503 又把“未知”伪装成“0 人”，且没有原地重试入口。

## 2. 产品与交互规则

- `POST 201` 返回的 Participant 是本次新增的权威结果，必须立即去重合并到弹窗名单；`DELETE 204` 是移除该 participant ID 的权威结果，必须立即从本地名单移除。
- 随后名单 GET 只负责并发校正。它失败时保留已知成功结果，提示“报名/取消已成功，名单同步暂时失败”，不得恢复旧项或鼓励重复提交。
- 写入成功后立即把已知名单长度同步到卡片、活动详情与其他已打开的 Topic 快照；精确 Topic GET 与列表 GET 只负责 revision/并发校正。列表 GET 失败不得清空广场或移除成功结果，只显示非阻断同步提示。
- 首次名单读取失败时人数状态为“暂不可用”，正文明确不能据此判断无人报名；不得显示“0 人/暂无记录”。错误区提供 44px 以上“重新读取名单”，成功后在原弹窗恢复真实名单。
- 完整名单基数未确认前不允许提交新的报名；先要求重新读取，避免把“本次新增 Participant”错误解释为全量名单。成功读取完整名单后才开放报名表单。
- 每次成功接受完整名单 GET 都把 `latest.length` 同步到卡片、活动详情、月/周历和议程；另一协作者刚报名时，打开名单即可校正跨视图人数。迟到读取不得覆盖更新请求的结果。
- 同步警告使用可感知错误区，异步结束后将焦点移入警告；名单、人数和底层 Topic 聚合不得互相矛盾。
- 只有 POST/DELETE 本身失败才表示本次报名操作未成功；阶段冲突仍关闭失效弹窗并同步最新 Topic。
- `409 PARTICIPANT_DUPLICATE` 表示当前已确认名单至少被另一协作者推进，不能作为不改变本地状态的普通表单错误。页面立即把旧人数标为未知、暂时关闭报名输入并读取完整名单：成功后显示“已在名单中，已刷新最新名单”，同步所有 Topic 快照的人数并把焦点移到结果；读取失败则保持“暂不可用”、提供“重新读取名单”，不得继续显示陈旧 0 人，也不得自动重放报名 POST。
- 取消报名收到稳定 `404 PARTICIPANT_NOT_FOUND` 同样表示名单已被另一协作者推进。页面立即失效旧人数并读取完整名单：成功后说明“该报名已由其他协作者取消，名单已刷新”，失败进入未知/重试；不能保留幽灵姓名或自动重放 DELETE。第二个 DELETE 必须零副作用且不推进 revision。
- 打开名单期间父 Topic 收到外部更高 revision 时，重读开始前先把完整名单基数标为未知并隐藏旧行/报名表；GET 失败不得一边声称“暂不可用”一边继续把旧子集作为完整名单展示或提供取消动作。重试成功后一次性恢复同快照正文、人数和 revision。由本弹窗自身 POST/DELETE 已知响应推进的 revision 已先记录为已覆盖，不触发第二次失效或清除成功提示。

## 3. 验收

桌面与 Pixel 7 真实执行 POST 201 + participants GET 503 + topics GET 503，弹窗仍显示新姓名与 1 人，卡片保留且同步为 1 人；再执行 DELETE 204 + 两类 GET 503，姓名立即消失、卡片为 0 人且不存在可重复取消按钮。两次均显示真实成功/同步暂缓提示，错误区获得焦点，受保护 API 名单与页面一致，不重放 mutation。另让首次 participants GET 返回 503，断言“暂不可用”、无虚假 0 人、报名提交不可用、可聚焦重试并恢复服务端既有姓名；让外部协作者报名后打开名单，断言完整 GET 校正所有跨视图人数。

并发同名验收：弹窗先确认 0 人，另一协作者成功报名同名，浏览器随后只发一次 POST 并收到 409；自动完整 GET 成功时名单、卡片、活动详情与月/周历均同步为 1 人且提示获得焦点。让该 GET 返回 503 时人数立即成为“暂不可用”、报名表单隐藏并提供可聚焦重试；恢复读取后显示唯一一条记录，全程不自动重放 POST。

并发取消验收：弹窗先确认 Alice/1 人，另一协作者 DELETE 204，浏览器随后只发一次 DELETE 并收到带稳定码的 404；成功恢复后弹窗、卡片、活动详情与日历为 0 人且提示聚焦。让恢复 GET 503 时隐藏旧 Alice、人数未知且可重试；最终只有第一个 DELETE 推进一次 revision。

外部 revision 验收：弹窗已确认甲/丙 2 人，另一协作者报名乙推进到 3 人，父列表先同步更高 revision，再让派生名单 GET 返回 503；页面立即显示“暂不可用”，不展示甲/丙旧子集、不开放报名或取消，重试后显示甲乙丙 3 人。自身报名后的既定恢复不额外重读或清除成功提示。

## 4. 回归证据

2026-09-02 初次验收：桌面 Chromium 与 Pixel 7 覆盖 POST/DELETE 成功后 participants/topics 双重 503、本地名单与卡片人数、非阻断同步提示、首次读取未知态与原地重试、未知基数阻断报名和完整名单跨视图传播；两次 mutation 均以受保护 API 核对且未重放。180 项 `npm run check` 与完整 E2E（123 通过、5 项职责跳过）通过。

第 32 轮独立旅程审计复现并发同名 409 后弹窗/卡片继续显示陈旧 0 人且无重试入口，本规格重新进入 Implementing；完成冲突读取恢复后回写终验。

终验：重复 409 立即失效旧基数并读取带 ETag/count 的完整名单；成功聚焦“已在名单中，已刷新”，503 则保持未知态、隐藏报名并提供重试，全程仅一次 POST。桌面/Pixel 7 新场景 4/4 定向通过；完整 E2E 127 通过、5 项职责跳过、0 失败/重试。

第 33 轮旅程审计复现双组织者取消同一记录时，第二个 404 后页面继续显示幽灵 Alice/1 人且无重读入口；本规格重新进入 Implementing，补齐取消方向的对称恢复后终验。

第 35 轮领域审计复现外部更高 revision 已到达但派生名单 GET 503 时，页面仍显示旧 2 人子集并提供取消动作，同时又称人数暂不可用。本规格继续保持 Implementing，补齐“先失效、后重读”的外部版本恢复。
