# SPEC-025：发布 / 认领后的排期连续转场

- 状态：`Accepted`
- 创建：2026-09-02
- 优先级：P2
- 关联：SPEC-004、SPEC-011、SPEC-018

## 1. 已复现断点

生命周期已经规定 `OPEN → CLAIMED → SCHEDULED`，但页面在以下两条路径成功后立即关闭弹窗，只给短暂 toast：

1. 发起人选择“我来分享”，服务端原子创建 `CLAIMED`；
2. 另一位伙伴认领 `OPEN`，服务端返回 `CLAIMED`。

用户随后必须在广场重新找到刚才的卡片，再点击“安排分享”。这不是数据缺失，而是状态之间没有可见过渡；移动端列表较长时尤其容易中断。

## 2. 产品决策

- “征集分享人”发布仍停在 `OPEN` 并返回广场，因为当前发起人没有承担分享责任，不能越过认领。
- “返回广场”是可验证的任务落点：无论发布前处于何种标签、日历视图、搜索或阶段条件，成功后都切换到 `OPEN + list`、清除临时条件并聚焦新 Topic 卡片，让发起人立即确认发布结果并继续编辑或邀请认领。
- “我来分享”和认领成功都使用服务端成功响应中的最新 Topic/revision，直接进入“安排炉边分享”表单。
- 进入排期表单不代表自动排期：页面明确说明前一步已经保存，排期是推荐下一步；时间未定可关闭，之后从“准备中”继续。
- 不把时间、地点塞回创建或认领表单；发布/认领已经持久化后，关闭排期不会回滚，也不得重复提交前一步。
- 直接从准备中卡片进入排期时不显示“刚刚完成”提示，避免伪造操作上下文。

## 3. 并发与恢复

- 转场使用成功响应的最新 revision，排期仍受既有 `If-Match`、未来时间和单轨防重叠规则保护。
- 排期失败保留当前表单和已保存议题；关闭后卡片仍为 `CLAIMED`。
- 关闭转场表单时切到“准备中”并聚焦目标 Topic 卡片，不能把焦点留在已卸载的创建/认领控件、body 或通用标题；该业务目标拥有本次关闭的回焦权，通用弹窗卸载回焦不得在后续动画帧覆盖它。
- 页面刷新与统计读取可并行进行，但不得覆盖或关闭转场中的排期表单。

## 4. 验收标准

1. 桌面与 Pixel 7 自荐发布成功后立即出现排期表单，提示“议题已发布并由你分享”和“可关闭后稍后安排”；仅一次创建请求。
2. 从 `OPEN` 认领成功后立即出现同一排期表单，提示认领已保存；仅一次认领请求。
3. 关闭转场表单后，新 Topic 保持 `CLAIMED`，页面显示“准备中”且目标卡片获得焦点；等待至少 1 秒后焦点仍稳定在该卡片，可从卡片再次排期。
4. 在转场表单直接提交后得到 `SCHEDULED`，不会再次创建或认领。
5. 从非 `OPEN` 标签、月/周历或带搜索条件的页面征集发布，仍只创建一次 `OPEN`，随后进入无筛选的 `OPEN + list` 并稳定聚焦新卡片；类型检查、构建和跨端 E2E 通过。
