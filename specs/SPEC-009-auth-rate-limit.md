# SPEC-009：认证抗猜测、短期协作会话与生产密钥强度

- 状态：`Accepted`
- 创建：2026-09-02
- 优先级：P1
- 关联：SPEC-003 第 13 轮、SPEC-004 FR-ACCESS-001、SPEC-008 口令叠层操作逻辑

> 2026-09-02 修订：FR-AUTH-001 的原始请求头传输、FR-AUTH-010 的 32 字符/随机强度门槛及相应验收已由 SPEC-016 取代。唯一验证入口、限流、短期会话、业务路由隔离和日志边界继续有效。

## 1. 问题、威胁模型与目标

共享围炉口令保护全部业务写入、参与名单和真实会议入口，但当前显式验证、全部写请求和两个敏感 GET 都直接比较原始口令，可以被分别用作无限在线猜测端点；浏览器还把原始口令长期放在 `sessionStorage`，生产启动则只检查口令非空。

确定性基线：从同一来源向 `POST /api/access/verify` 并发提交 200 个错误候选，当前全部返回 `401`、没有 `429`；随后正确口令仍返回 `204`。相同候选也可改投受保护业务路由。Topic 数量和 revision 不变，说明当前问题是认证边界可猜测，而非一次请求已造成越权写入。

本规格采用两层凭证：

1. **原始共享口令**只允许提交给 `POST /api/access/verify`，该唯一入口做基于可信来源和全局容量的固定限流。
2. 验证成功后服务端签发短期、高熵、不可伪造的**协作会话令牌**；业务写请求、参与名单和会议入口只验证令牌，不再读取或比较原始口令。

目标：关闭全部口令猜测旁路；让已经解锁的协作者不受同一 NAT 下其他人的错误尝试影响；不在浏览器持久化原始口令；明确令牌期限、轮换失效、旧客户端迁移、退出、错误优先级、数据不变式、内存与日志边界；生产环境拒绝弱口令启动。

## 2. 凭证边界与 API 契约

### FR-AUTH-001 唯一口令候选入口

- 只有 `POST /api/access/verify` 读取 `X-Fireside-Write-Key` 并比较共享口令；新客户端按 SPEC-016 使用版本化 UTF-8 base64url，旧 ASCII 原文仅在缺少 encoding 头时兼容。
- 以下受保护业务入口统一只读取 `X-Fireside-Session`：
  - 除 `/api/access/verify` 外的全部业务 `POST / PATCH / DELETE`；
  - `GET /api/topics/:id/participants`；
  - `GET /api/topics/:id/meeting-access`；
  - `GET /api/access/session`。
- 受保护业务入口即使收到正确的 `X-Fireside-Write-Key`，只要没有有效协作令牌，也必须返回 `401 ACCESS_SESSION_REQUIRED`；不得静默换发令牌、比较口令或消耗口令限流桶。
- 健康页、`GET /api/access`、Topic 列表/详情、统计和静态资源保持公开，不读取任何认证头。
- 新增受保护路由必须复用同一个会话令牌守卫，不得重新接受原始口令或自行实现另一套认证分支。
- 守卫必须依据 Fastify 已解析的路由模板识别敏感资源，不能用原始 URL 字符串正则猜测路由；参数段或静态段使用合法百分号编码时仍须命中同一守卫。
- Fastify 为敏感 `GET` 自动暴露的 `HEAD` 必须与对应 `GET` 使用相同会话守卫；无令牌时稳定 `401`，不得以 `Content-Length`、状态差异或服务端异常泄露资源是否存在或响应尺寸。

### FR-AUTH-002 验证与会话校验契约

认证已启用时，正确且未被限流的 `POST /api/access/verify` 返回 `200`：

```json
{
  "sessionToken": "v1.<issuedAt>.<expiresAt>.<nonce>.<mac>",
  "expiresAt": "2026-09-02T18:00:00.000Z"
}
```

- 验证请求只通过 SPEC-016 定义的版本化 `X-Fireside-Write-Key` 发送口令等价编码，不允许把口令放入 URL、query、cookie 或业务请求体。
- `GET /api/access/session` 使用 `X-Fireside-Session` 校验当前会话；有效时返回 `200 { "valid": true, "expiresAt": "..." }`，缺失、畸形、过期、签名错误或由旧口令签发时统一返回 `401 ACCESS_SESSION_REQUIRED`。
- `POST /api/access/verify` 和 `GET /api/access/session` 的成功响应，以及参与名单与会议入口响应，均带 `Cache-Control: no-store`。
- 认证未启用只允许发生在测试或明确的非生产本地模式：验证和会话校验均返回 `204`，业务路由保持既有开放行为；生产不得进入该分支。
- `GET /api/access` 继续只返回是否启用认证，不接受候选、不签发会话、不消耗桶。

### FR-AUTH-003 自定义头而非 cookie

- 浏览器仅把协作令牌存入当前 origin 的 `sessionStorage`，键名固定为 `fireside-collaboration-session-v1`；原始口令只存在于 AccessModal 输入值和本次验证调用中，验证结束立即清空，不写入任何 Web Storage。
- 所有受保护业务请求显式设置 `X-Fireside-Session`。不得使用 cookie、URL 参数或 `localStorage`，避免浏览器自动附带凭证所带来的 CSRF 与跨会话长期暴露。
- 服务端不启用宽泛 CORS；跨源页面不能读取验证响应或自行附加自定义会话头。该设计不声称抵抗同源 XSS，XSS/CSP 加固独立处理。

## 3. 短期协作令牌

### FR-AUTH-004 格式、签名与有效期

选择**无服务端会话表的签名令牌**，而不是进程内 token Map：当前是单实例共享权限，不需要逐用户会话数据；无状态令牌在同一口令下可跨进程重启继续使用，也不会因签发次数增长占用内存。

- 令牌为 `v1.<issuedAt>.<expiresAt>.<nonce>.<mac>`；时间是十进制 Unix 秒，`nonce` 是密码学安全随机源生成的 16 字节 base64url，`mac` 是 32 字节 HMAC-SHA-256 base64url。
- HMAC 密钥通过 `HKDF-SHA-256(IKM=UTF8(writeKey), salt=UTF8("fireside-auth-v1"), info=UTF8("collaboration-session-signing-v1"), L=32)` 派生，不能把原始口令直接放入令牌。
- MAC 覆盖 `v1.<issuedAt>.<expiresAt>.<nonce>` 的 ASCII 原文；解析先校验总长度、段数和字符集，再以定长缓冲区和 timing-safe compare 验证 MAC。
- 签发时间取注入时钟向下取整的 Unix 秒，TTL 固定为 `8 小时（28,800 秒）`，不可由客户端指定或续期；有效条件为 MAC 正确、`expiresAt - issuedAt = 28,800`、`expiresAt > now`，且 `issuedAt` 不得晚于服务端当前时间 60 秒以上。响应的 ISO `expiresAt` 必须与令牌秒值精确对应。
- 令牌正文不包含原始口令、Topic、参与者、会议 URL、来源 IP 或其他业务信息。原始令牌只允许出现在验证成功响应和 `X-Fireside-Session` 请求头中。
- 校验器接受注入时钟和随机源，以便确定性覆盖签发、过期、未来时间、篡改和随机 nonce；base64url 段不带 `=` padding，超过 160 ASCII 字节的令牌或任何畸形令牌在 HMAC 前稳定失败。

取舍：无状态令牌不能单独撤销某一个已泄露会话；本轮以 8 小时 TTL、退出清除和共享口令轮换全量失效控制暴露窗口。逐会话撤销、用户身份和多设备管理属于未来账号体系，不为此引入持久 token 表。

### FR-AUTH-005 轮换、启动与退出

- 签名密钥由当前 `FIRESIDE_WRITE_KEY` 派生；共享口令轮换并重启后，全部旧令牌因 MAC 不匹配立即失效，同一原始口令重启则未过期令牌继续有效。
- 页面启动时先读新会话键并请求 `/api/access/session`；无效或过期则清除存储和内存副本，恢复锁定态。校验不会刷新 TTL。
- 存储中存在任意 token 不能让页面乐观进入已解锁态；`/api/access` 与 `/api/access/session` 全部成功前保持失败关闭。任一请求超时或网络失败都清除无效 token、停留锁定态且不得产生未处理 Promise。
- 已解锁界面必须提供“退出协作”入口。退出只在客户端原子清除会话键和内存副本，关闭/清空正在展示的参与名单、真实会议信息等敏感数据，并恢复锁定态；无状态服务端不提供虚假的单 token 撤销接口。
- 退出不得提交或自动重放业务动作；公开 Topic 数据可以保留，未提交的公开业务草稿可以保留但再次提交时必须重新解锁。
- 每次成功解锁、会话失效和退出都推进客户端会话代际；任何旧代际发出的参与名单、会议入口或带敏感字段的异步响应即使随后成功返回，也必须被丢弃，不能重新打开弹窗或恢复已清空的秘密。

## 4. `/verify` 抗猜测限流

### FR-AUTH-006 可信 client IP

- 当前 Fastify 直接监听主机端口，没有受信反向代理；来源键使用 TCP 连接得到的 `request.ip`。
- `trustProxy` 保持关闭。不得从 `X-Forwarded-For`、`Forwarded`、`X-Real-IP` 或任意客户端头生成来源键；伪造这些头不得切换桶。
- IPv4-mapped IPv6 与其 IPv4 等价表示归入同一来源键。无法取得合法 IP 时使用共享 `unknown` 桶，不为每个请求生成新键。
- 未来引入反向代理前必须新增独立规格，限定可信代理地址/网段并增加伪造头验收；不得直接信任所有代理。

### FR-AUTH-007 窗口、容量和成功/失败桶语义

仅 `POST /api/access/verify` 使用注入时钟驱动的 60 秒滑动窗口：

| 桶 | 容量 | 语义 |
| --- | --- | --- |
| 单 TCP 来源 | 10 次失败 | 前 10 个错误候选返回 `401`，此后所有候选在恢复前均为 `429` |
| 全局 | 200 次失败 | 全部来源累计 200 个错误候选后，此后所有候选在恢复前均为 `429` |

- 每次验证先原子清理过期记录并检查两个桶；任一桶已满时**不比较候选**，即使这次口令正确也返回 `429`。此规则避免 `429/成功` 成为口令正确性旁道，也确保阻断期不可绕过。
- 两个桶均有容量时才比较口令。缺失、空或错误候选记录一次失败并返回 `401 ACCESS_REQUIRED`；正确候选签发令牌、清空该来源失败桶，但不清空全局失败记录。
- 一个请求只记录一次失败。已满时不继续追加时间戳；同来源从空桶并发 12 个错误候选必须严格得到 10 个 `401` 和 2 个 `429`。
- 每次决策前删除 `timestamp <= now - 60s` 的记录，恰在边界的记录已过期。多个桶阻断时，`Retry-After` 取恢复全部阻断桶所需秒数最大值。
- 时钟无效或倒退不得提前清桶或产生非正等待；以最近一次有效时间为下限，`Retry-After` 至少 1 秒。
- 受保护业务入口的会话缺失/无效/过期只返回 `401 ACCESS_SESSION_REQUIRED`，不进入共享口令失败桶；高熵签名令牌不是可行的口令猜测旁路。

### FR-AUTH-008 稳定错误契约

错误口令且容量未满：

```json
{ "code": "ACCESS_REQUIRED", "message": "围炉口令不正确" }
```

已阻断的验证请求：

```json
{ "code": "ACCESS_RATE_LIMITED", "message": "尝试过于频繁，请稍后再试" }
```

无效会话访问业务或会话校验：

```json
{ "code": "ACCESS_SESSION_REQUIRED", "message": "协作会话已失效，请重新输入围炉口令" }
```

- `429` 必须带十进制整数秒 `Retry-After`，取值 `1..60`。
- 三类拒绝响应不得包含候选口令、摘要、会话令牌、生产口令、Topic/参与者/会议数据、桶历史或全局余量。
- AccessModal 收到 `429` 时保持顶层、保留底层业务草稿并展示消息和可用等待时间，不自动重试；阻断期内输入正确口令也仍显示 `429`。
- 业务请求的 `401 ACCESS_SESSION_REQUIRED` 才清除本地旧令牌并进入既有 pending-action 解锁流程；不得把业务 `401` 当成一次口令失败。

### FR-AUTH-009 有界内存与清理

- 限流器是独立纯逻辑组件，接受注入时钟；路由不得各自维护 Map。
- 来源 Map 最多 `10,000` 个键，每个键最多 `10` 个时间戳；全局最多 `200` 个时间戳。签名会话本身不进入服务端 Map。
- 每累计 256 次实际记录的失败，扫描至多 256 个来源并保留游标供下次续扫；请求命中的来源也立即惰性清理。
- 达到 10,000 个来源时，新来源写入前按最近使用顺序确定性淘汰最久未使用项；来源淘汰不得删除全局记录。
- 不创建常驻定时器；应用关闭后无遗留句柄，重启可清空失败桶。来源键与时间戳外不得保存候选、摘要、认证头或请求体。

## 5. 生产密钥与秘密处理

### FR-AUTH-010 生产启动失败关闭

`NODE_ENV=production` 时，`FIRESIDE_WRITE_KEY` 必须同时满足：

- 已配置且与自身 `trim()` 完全相同，不允许首尾空白；
- Unicode code point 长度为 `6..256`；按用户要求不再附加占位词或重复字符限制。

任一条件不满足必须在监听端口和打开数据库前拒绝启动，错误只说明配置要求，不回显值、长度、摘要或派生信息。长度检查只是可执行的最低门槛，不声称能测量真实熵；当前部署值存入 Git 外的 `0600` 环境文件。

文档示例不得把真实口令放入 shell 命令参数、仓库、systemd unit、日志或 URL。部署前以不输出值的预检确认现有配置满足约束；若不满足，先安全轮换再发布失败关闭逻辑，避免服务重启循环。非生产测试注入和明确本地开发可使用短测试值，不得削弱生产入口。

### FR-AUTH-011 日志、缓存与响应脱敏

- Pino 显式脱敏 `req.headers.x-fireside-write-key` 和 `req.headers.x-fireside-session`；不得复制候选、摘要、签名密钥、完整 token 或请求头到其他日志字段。
- 验证成功响应是唯一返回完整会话令牌的响应；除此之外任何响应、错误或日志都不得包含口令或令牌。敏感成功响应按 FR-AUTH-002 使用 `no-store`。
- 首次进入 `429` 可记录结构化安全事件，字段限于事件名、路由类别和等待秒数；同一来源同一窗口的后续 `429` 不逐条写 error 日志。
- `401 / 429` 是预期安全事件，不记录异常堆栈、不升级为通用 `500`。自动化必须用测试秘密扫描捕获日志和除验证成功外的响应。

## 6. 错误优先级与数据不变式

### FR-AUTH-012 固定优先级

`POST /api/access/verify` 的顺序为：解析认证头所需最小信息 → 限流预检 → 未阻断时比较口令 → 失败计桶或成功签发。阻断期内不比较候选。

其他受保护入口在 body 解析前验证 `X-Fireside-Session`：

1. 缺失/无效/过期会话返回 `401 ACCESS_SESSION_REQUIRED`。
2. 只有有效会话才进入 body、`If-Match`、实体、revision、状态和活动阶段校验。

因此无效会话与 malformed JSON、非法 `If-Match`、不存在 Topic、陈旧 revision 或阶段冲突同时出现时稳定返回 `401`，不得泄露后续条件；有效会话继续得到既有 `400 / 404 / 409 / 412 / 428` 或成功。业务入口永不返回口令限流的 `429`。

### FR-AUTH-013 拒绝路径不变式

任意认证 `401 / 429` 后必须保持：

- Topic 数量、业务字段、revision、position 和全局 order version 不变；
- 参与名单、participantCount、归档材料和活动阶段不变；
- 会议 URL、参与者姓名、原始口令和会话令牌不出现在拒绝响应或日志中；
- SQLite 不创建空事务、副作用记录或审计时间更新。

验证失败桶是唯一允许变化的服务端状态，且仅 `verify` 的容量内错误候选改变它。

## 7. 浏览器迁移与完整旅程

### FR-AUTH-014 旧客户端硬切迁移

- 新前端首次启动必须删除旧键 `fireside-write-key`，不得读取、发送或自动用其中的旧原始口令换取令牌。
- 部署后旧静态客户端若继续向业务路由发送 `X-Fireside-Write-Key`，服务端忽略该头并返回 `401 ACCESS_SESSION_REQUIRED`；不设兼容宽限，否则业务路由仍可被用于猜口令。
- 用户重新输入一次口令获得会话；之后刷新当前 tab 通过 `/api/access/session` 恢复解锁，8 小时到期或口令轮换后再次提示。
- 原始口令在验证成功、失败、限流、关闭弹窗和组件卸载路径上均从输入状态清除；不在开发日志、错误对象或埋点中保留。

### FR-AUTH-015 401、429 与 pending action

- 业务 `401 ACCESS_SESSION_REQUIRED` 保持 SPEC-008：打开顶层 AccessModal、底层 inert、草稿保留；成功解锁只关闭 Access 层，不自动重放已经发出的写请求，用户需再次显式提交。
- 按 SPEC-018，发起议题是公开业务意图：锁定时先打开并填写创建表单，首次发布在客户端打开 AccessModal 且不发送写请求；解锁后仍由用户再次显式发布。直接“解锁协作”则不创建业务草稿。
- 一次真实业务 401 已把页面置为已知锁定后，关闭 AccessModal 再次提交只重开验证层并保留表单，不重复发出注定失败的业务请求；429 倒计时关闭重开也保持零业务写入。
- 对尚未发送、必须先解锁的入口动作，成功后只续接最新一个 pending action；退出、关闭 AccessModal 或验证失败均不得执行它。
- `429` 只可能来自 AccessModal 的 `/verify`，不清除底层草稿或误报解锁。正确口令在 `Retry-After` 到期前也不绕过。
- 已持有有效会话的协作者即使与攻击者共享 NAT，业务写、参与名单和会议入口仍正常；攻击者填满 `/verify` 桶只影响新会话签发。

## 8. 单实例边界与非目标

- 限流桶是当前单 Node.js 进程内存状态；systemd 单实例满足该假设，重启会清桶。多实例前必须使用共享限流存储或可信网关并新增一致性规格。
- 会话令牌是无状态签名凭证，不受限流进程重启影响；口令轮换或 8 小时到期使其失效。
- 本轮不实现个人账号、cookie 会话、验证码、永久封禁、IP 管理、单令牌服务端撤销、多设备清单或自动续期。
- 本轮不启用代理信任，不解决纯 HTTP、systemd root/数据库文件权限、Fastify 解析错误映射、周历报名或移动触控热区；这些风险继续留在 SPEC-003。
- 本轮不限制公开只读请求，也不对有效会话的正常业务吞吐施加 `/verify` 限流。

## 9. 验收矩阵

### 9.1 单元与纯逻辑

1. 同来源前 10 次错误验证为认证失败，第 11 次限流；`Retry-After` 依次覆盖 60、1 和恰在 60 秒边界恢复。
2. 12 个并发错误严格为 10 个未限流失败和 2 个限流；阻断期正确候选也为 `429` 且未执行比较/签发。
3. 200 个实际来源填满全局桶；下一来源被阻断。容量恢复后正确候选签发并只清本来源桶，不清全局历史。
4. 伪造 `X-Forwarded-For / Forwarded / X-Real-IP` 不切换 TCP 来源桶；IPv4-mapped IPv6 归一化。
5. 10,001 个来源不超过 Map 上限；每轮至多扫描 256 项，LRU/游标/边界过期确定性，无效或倒退时钟不绕过容量且无常驻句柄。
6. 固定时钟/随机源签发两个不同 nonce 的令牌；有效、到期、未来签发、任一段篡改、错误段数/字符/超长、错误口令派生密钥全部稳定校验。
7. 生产口令覆盖缺失、空、首尾空白、5/6/256/257 code point、重复字符与 Unicode；失败在 DB 打开与 listen 前且消息不含输入片段。

### 9.2 API、迁移与数据不变式

1. `/verify` 容量内错误为 `401 ACCESS_REQUIRED`，阻断为带整数 `Retry-After` 的 `429 ACCESS_RATE_LIMITED`，正确且未阻断时返回 TTL 精确的 token；所有路径不双计数。
2. 每一类受保护写、参与名单、会议入口和 `/access/session` 只接受有效 `X-Fireside-Session`；缺失、畸形、过期、篡改、旧签名和仅提供正确原始口令都为稳定 `401 ACCESS_SESSION_REQUIRED`，且不改变验证桶。
   - 对参与名单、会议入口和会话校验分别覆盖普通 GET、参数段百分号编码、静态段百分号编码和 HEAD；所有变体必须经过同一守卫，不得泄露正文、存在性或长度。
3. 有效会话跨路由复用并得到既有业务结果；共享口令轮换后旧 token 全部失效，新口令验证签发的新 token 生效，同口令应用重启不使未过期 token 失效。
4. 无效会话叠加 malformed JSON、非法 `If-Match`、404、revision 和活动阶段冲突时验证认证优先；有效会话验证既有错误顺序。
5. 认证拒绝前后比较 Topic 全列、revision/position/order version、参与名单和计数；除验证成功外的响应及全部捕获日志均不含测试口令、token、会议 URL 或参与者姓名。
6. 旧业务头不会换取访问或计桶；前端启动删除旧 storage key，只在新键保存 token。退出后新键、内存会话和已展示敏感数据均消失。

### 9.3 桌面 Chrome 与 Pixel 7

1. 新用户输入口令后只在 `/verify` 请求看到版本化 ASCII 等价编码；后续写、名单、会议请求只带会话头。刷新同 tab 经 `/access/session` 恢复，过期/轮换后回到锁定态。
   - 无效 token、延迟校验和 `/api/access` 或 `/api/access/session` 网络失败期间不得短暂显示“协作已解锁”或开放受保护入口；恢复成功后才切换状态。
2. 在已有业务草稿的 401 叠层中错误验证直至 `429`：AccessModal 保持顶层、焦点留在错误/输入区域、底层 inert、草稿与滚动锁不变；阻断期正确输入仍不关闭。
3. 在独立的未阻断测试实例中，正确验证只关闭 Access 层且不自动重放已发写请求，再次显式提交成功一次；未发送入口动作仅续接最新一项。60 秒恢复边界由注入时钟的单元/API 测试覆盖，双端测试不得通过真实长等待拖慢或制造不稳定性。
4. 一个已持有有效 token 的浏览器与同来源攻击流并行：攻击流触发 `/verify 429`，已解锁浏览器仍能写入、查看名单和取得会议入口。
5. “退出协作”立即清除 token 并关闭参与名单/会议敏感展示；再次保护操作需解锁。旧 storage 迁移、Esc/X/backdrop、逐层焦点和 SPEC-008 全部回归。
   - 延迟一个真实会议入口或参与名单响应，在响应返回前退出或触发会话失效；放行迟到的 `200` 后页面仍保持锁定、无敏感弹窗、无原始链接/姓名且 storage 为空。
6. 429 浏览器旅程必须命中真实测试服务限流器而非完全伪造响应；测试环境可通过 `AppOptions` 使用短窗口/小容量，但响应必须来自真实 `/verify`，并由另一个保存有效 token 的浏览器页面完成至少一次真实业务写，证明共享来源隔离。
