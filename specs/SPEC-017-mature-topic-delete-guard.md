# SPEC-017：成熟议题永久删除保护

- 状态：`Accepted`
- 创建：2026-09-02
- 最后更新：2026-09-02
- 优先级：高价值 P2
- 依赖：SPEC-002、SPEC-004、SPEC-005、SPEC-007
- 来源：SPEC-003 第 19 / 21 轮独立业务、API 与 UX 审计

## 1. 问题与目标

当前 `DELETE /api/topics/:id` 只校验 id 和 revision，页面也向所有状态展示“删除”。SQLite 会级联删除参与名单，因此协调者只需两次点击就能永久抹掉已排期活动、报名伙伴、会议安排，或已经归档的知识沉淀。这绕过了取消排期、未举行和撤销归档等明确的业务路径，也违背“删除只用于误建或重复议题”的产品承诺。

本规格把永久删除收口为早期内容纠错操作，不再让它承担取消活动、纠正排期或撤销归档的职责。目标是：

1. 已进入活动履约或知识沉淀阶段的议题不能被一步永久删除。
2. 用户仍能沿既有生命周期纠正误排、未举行和误归档，并在回到早期状态后明确删除。
3. 拒绝路径对 Topic、报名、排序和版本完全零副作用。
4. 页面只展示真实可执行动作，确认文案准确表达不可恢复性和协作责任。

## 2. 产品决策

### DEC-017-001 删除是早期内容纠错，不是生命周期动作

| 当前状态 / 阶段 | 直接永久删除 | 用户应走的路径 |
| --- | --- | --- |
| `OPEN` | 允许 | 仅用于误建、测试或重复议题 |
| `CLAIMED` | 允许 | 删除分享人署名和内容；若只是暂不分享，应选择“重新开放” |
| `SCHEDULED / UPCOMING` | 禁止 | 改期保留报名；取消活动先“取消排期”，清空报名和会议安排后回 `CLAIMED` |
| `SCHEDULED / LIVE` | 禁止 | 活动进行中不能取消或删除；结束后按真实结果处理 |
| `SCHEDULED / ENDED` | 禁止 | 已举行则归档；确未举行则“未举行 / 重新排期”回 `CLAIMED` |
| `ARCHIVED` | 禁止 | 误归档先“撤销归档”；随后按结束活动的真实情况处理 |

- `DELETE` 成功时不得存在排期、归档资料或报名可被隐式级联清除。
- 共享围炉口令只代表协调者能力，没有个人账号时不伪称只有发起人或分享人可删除。
- 系统没有回收站，不能把生产备份宣传成用户可用的恢复能力。

### DEC-017-002 并发与状态错误优先级保持全站一致

请求已通过会话与 `If-Match` 语法门禁后，在同一个立即写事务内依次判断：

1. id 不存在：`404 TOPIC_NOT_FOUND`；
2. revision 不同：`412 TOPIC_REVISION_CONFLICT`，返回 `currentRevision`；
3. revision 相同但状态不是 `OPEN / CLAIMED`，或发现任何不应存在的成熟依赖：`409 TOPIC_DELETE_STATE_CONFLICT`；
4. 只有通过全部守卫才执行删除。

陈旧快照与成熟状态同时存在时先返回 `412`，让客户端先同步权威快照；使用最新 revision 重试仍因成熟状态得到 `409`。这一顺序延续 SPEC-005 与 SPEC-007 的并发契约。

## 3. 服务端契约

### FR-DELETE-001 原子状态门禁

`DELETE /api/topics/:id` 必须在 `BEGIN IMMEDIATE` 内：

- 读取 Topic 的 `revision`、`status` 及删除安全所需字段；
- 按 DEC-017-002 返回稳定错误；
- 防御性确认允许状态没有排期、归档字段和参与记录；异常数据同样以 `409 TOPIC_DELETE_STATE_CONFLICT` 拒绝，不做静默清理；
- 使用同时匹配 `id + revision + status IN ('OPEN','CLAIMED')` 的 DELETE；
- 删除后压实其余 Topic 的 `position`，只把 `orderVersion` 精确推进一次；其余 Topic revision 不变；
- 在事务内取得此次操作产生的 orderVersion，并以 `X-Order-Version` 返回，不能在事务外重读到其他并发写的更晚版本。

稳定 `409` 响应至少包含：

```json
{
  "code": "TOPIC_DELETE_STATE_CONFLICT",
  "message": "已排期议题不能直接删除，请先按活动实际情况取消排期或标记未举行",
  "currentRevision": 3,
  "currentStatus": "SCHEDULED"
}
```

归档态文案为“归档记录不能直接删除；如为误归档，请先撤销归档”。响应不得包含报名姓名、会议链接或归档内容。

### FR-DELETE-002 零副作用

任何 `404 / 412 / 409` 删除失败均不得改变：

- Topic 任一字段与 revision；
- 参与者记录与 participantCount；
- position 顺序；
- orderVersion；
- 会议入口、收获和资料链接。

## 4. 页面操作与反馈

### FR-DELETE-UI-001 只展示可执行入口

- 仅 `OPEN / CLAIMED` 且公开快照未带排期、报名、会议或归档依赖时，列表卡维护区展示“删除”；`SCHEDULED / ARCHIVED` 与异常早期数据不展示。页面从公开快照派生该能力，规则与服务端防御性守卫同构。
- 日历事件和活动详情不新增绕过卡片门禁的删除入口。
- 成熟状态继续展示当前阶段的纠错动作：取消排期、未举行 / 重新排期、撤销归档；`LIVE` 只说明活动进行中，等待结束后按实际结果处理。

### FR-DELETE-UI-002 明确确认与安全默认

- 删除弹窗的初始焦点落在明确的“取消”按钮；Esc、遮罩和取消均关闭且不发请求，并恢复到原删除按钮。
- `OPEN` 文案：“删除只适用于误建或重复议题。议题内容将永久移除，此操作不可撤销。”
- `CLAIMED` 文案额外显示分享人已认领，说明内容和分享人署名都会永久移除；若只是不再分享，应关闭并选择“重新开放”。
- 危险提交按钮使用“确认永久删除”，与普通确认动作明确区分。
- 成功删除后刷新列表，并把稳定焦点移到“议题广场”标题，而不是已卸载的触发按钮或 `body`。

### FR-DELETE-UI-003 并发恢复

- `412`：关闭旧确认、同步最新 Topic，不自动重放；若最新状态仍为 `OPEN / CLAIMED`，焦点回到最新版删除按钮，用户必须重新打开确认；若已进入成熟状态，删除入口自然消失，焦点回到对应议题卡。
- `409 TOPIC_DELETE_STATE_CONFLICT`：关闭旧确认并同步权威状态，删除入口消失，焦点回到该议题卡，让当前取消排期、未举行或撤销归档动作可被继续发现。
- `404 TOPIC_NOT_FOUND`：关闭旧确认、同步移除陈旧卡片，提示“议题已由其他协作者删除，无需重复操作”，焦点移到议题广场标题。
- 成功、冲突和缺失后的焦点安排必须等待最新列表稳定渲染，不能恢复到已卸载节点。

## 5. 验收矩阵

### 5.1 API / 数据

1. `OPEN`、`CLAIMED` 使用当前 revision 删除均为 204；position 连续、`orderVersion +1`，其余 revision 不变。
2. `SCHEDULED / UPCOMING` 带报名直接删除为 409，Topic、报名、会议安排、position 和 orderVersion 原样保留；取消排期后人数归零、回 `CLAIMED`，再确认删除成功。
3. `SCHEDULED / LIVE` 删除与取消排期均拒绝，数据原样保留。
4. `SCHEDULED / ENDED` 删除拒绝；分别验证“完成归档”和“未举行 / 重新排期”两条正向路径。
5. `ARCHIVED` 带参与名单、收获和资料时删除拒绝且全部保留；撤销归档不会自动获得删除资格。
6. 陈旧 revision 对成熟状态先返回 412；使用 `currentRevision` 再试返回 409。
7. 异常 `OPEN / CLAIMED` 数据若带报名、排期或归档依赖，删除 409 且零副作用。
8. 拒绝删除不使旧排序快照失效；成功删除才推进 orderVersion；响应头精确等于本事务产生的版本。
9. 双数据库连接确定性交错验证读取、状态推进和删除不会绕过门禁。

### 5.2 桌面 Chrome / Pixel 7

1. 状态矩阵中只有 `OPEN / CLAIMED` 出现删除；日历和活动详情没有删除入口。
2. 删除弹窗默认聚焦取消；取消、Esc 恢复原按钮；成功删除聚焦议题广场标题。
3. OPEN 与 CLAIMED 文案、分享人影响和“确认永久删除”准确。
4. UPCOMING 带报名通过“取消排期 → CLAIMED → 删除”完成，确认报名和会议安排先被明确清空。
5. ARCHIVED 通过“撤销归档 → 未举行 / 重新排期 → CLAIMED → 删除”完成；LIVE 不出现取消或删除。
6. 删除确认期间同状态内容被远端更新，页面收到 412、同步且不自动删除；重新确认后才能成功。
7. 删除确认期间远端把议题推进到成熟状态，页面收到 412、同步后移除删除并保留成熟数据与对应动作。
8. 异常 `OPEN / CLAIMED` 公开快照不展示删除；陈旧页面收到 409 后同步并移除入口，不形成重复失败死循环。
9. 确认期间另一协作者已删除议题时，404 关闭弹窗、移除卡片并聚焦议题广场标题。
10. 合法极限 80 字符连续标题与 30 字符连续分享人不会撑宽删除弹窗；桌面与 Pixel 7 均无页面/弹窗横向溢出，取消和永久删除按钮保持可见且至少 44px。

## 6. 兼容与测试清理

- SPEC-002“任意议题均可删除”由本规格替代。
- SPEC-005“最新 revision 再次确认即 204”增加状态门禁：只有最新版仍为 `OPEN / CLAIMED` 才成立。
- 自动化测试不得为方便清理而绕过业务契约；成熟夹具先执行 `unarchive / unschedule` 归一到 `CLAIMED`。进行中的短命夹具在隔离数据库结束时整体销毁，不伪造非法删除。
- 原“已排期议题在海报打开前被直接删除”的用例已不再是合法生产竞态，改为取消排期造成海报资格失效；删除缺失态由允许删除的早期议题覆盖。
