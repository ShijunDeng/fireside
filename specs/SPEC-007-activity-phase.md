# SPEC-007：活动阶段与动作准入

- 状态：`Accepted`
- 创建：2026-09-02
- 优先级：P1
- 关联：SPEC-003 第 11 轮、SPEC-004 FR-FLOW-004 / FR-JOIN-001～002 / FR-POSTER-001、SPEC-005 Topic revision

## 1. 问题与目标

数据库状态 `SCHEDULED` 同时承载尚未开始、正在进行和已经结束三种真实场景，现有 API 只检查持久状态，造成正常操作即可复现的矛盾：过去时间仍能排期；未来或进行中的活动可提前归档；结束后仍能新增/取消报名并读取真实会议入口；归档后会议入口仍可取；页面一到开始时刻就显示“待归档”，却同时保留报名、会议、取消排期和归档动作。

本规格不增加容易漂移的 `LIVE` 数据库状态，而是用 `scheduledAt + duration + 权威当前时间` 派生阶段，让服务端作为最终准入边界，前端同步表达用户当下真正能做的事。

目标：

1. 排期前、进行中、结束后的动作矩阵唯一且前后端一致。
2. 结束或归档后不再返回真实会议入口，不再污染历史报名名单。
3. 活动不能在尚未完成时被归档；未举行的活动可以安全回到准备中重新排期。
4. 页面无需刷新也会跨越开始/结束边界，更新徽标、文案与动作。
5. 所有时间冲突均稳定失败，不推进 revision、不删除报名、不泄漏会议 URL。

## 2. 派生阶段

新增前后端共享纯函数 `activityPhase(scheduledAt, duration, now)`。只有信息完整的 `SCHEDULED` 议题具有活动阶段：

| 阶段 | 精确边界 | 页面语义 |
| --- | --- | --- |
| `UPCOMING` | `now < start` | 已排期 / 即将开始 |
| `LIVE` | `start <= now < start + duration` | 进行中 |
| `ENDED` | `now >= start + duration` | 待归档 |

- `start` 为 `scheduledAt` 的绝对时刻，`duration` 以分钟计算；结束边界不得用本地时区字符串比较。
- `now === start` 立即进入 `LIVE`；`now === end` 立即进入 `ENDED`。
- 无效或缺失的排期数据返回 `null`，不得猜测阶段；服务端对此类历史异常数据拒绝依赖时间的动作并返回可诊断错误。
- 持久状态继续只有 `OPEN / CLAIMED / SCHEDULED / ARCHIVED`；阶段不写数据库，不做后台迁移。

## 3. 权威动作矩阵

| 动作 | UPCOMING | LIVE | ENDED | ARCHIVED / 非 SCHEDULED |
| --- | --- | --- | --- | --- |
| 报名 / 取消报名 | 允许 | 允许，支持迟到参与 | 拒绝 | 拒绝 |
| 读取报名名单 | 允许 | 允许 | 允许，只读 | 允许，只读 |
| 获取真实会议入口 | 允许 | 允许 | 拒绝 | 拒绝 |
| 生成宣讲海报 | 允许 | 拒绝 | 拒绝 | 拒绝 |
| 改期或更改时长 | 允许，结果仍须为未来 | 拒绝 | 拒绝 | 按既有状态规则 |
| 修正地点 / 会议链接 | 允许 | 允许，便于现场纠错 | 允许但入口保持关闭 | 归档态按既有只读规则 |
| 普通内容编辑 | 允许 | 允许 | 允许 | 允许 |
| 取消排期 | 允许 | 拒绝 | 仅通过“未举行 / 重新排期”语义允许 |
| 完成归档 | 拒绝 | 拒绝 | 允许 | 不适用 |
| 永久删除 Topic | 拒绝 | 拒绝 | 拒绝 | `ARCHIVED` 拒绝；仅 `OPEN / CLAIMED` 允许（SPEC-017） |

### FR-PHASE-001 排期必须在未来

- `POST /schedule` 的 `scheduledAt` 必须严格晚于该请求捕获的权威 `now`；等于或早于 `now` 均以 `400 ACTIVITY_TIME_INVALID` 拒绝。
- 对 `SCHEDULED` 议题 PATCH `scheduledAt` 或 `duration` 时，只有当前阶段为 `UPCOMING` 才允许，且修改后的开始时刻仍须严格晚于同一次请求的 `now`。
- 时间字段失败时不改变任何字段或 revision。日期输入应设置合理的前端最小值，但浏览器校验不能替代服务端。

### FR-PHASE-002 报名与会议入口

- 报名新增、按参与者 ID 取消报名必须在写事务读取 Topic 后，用事务内捕获的单一 `now` 校验阶段；仅 `UPCOMING` / `LIVE` 可写。
- `ENDED` 后名单冻结；受保护的名单 GET 继续允许协调者在结束/归档后查看。
- `GET /meeting-access` 必须同时满足 Topic 为 `SCHEDULED`、阶段为 `UPCOMING` 或 `LIVE`、且存在可用 URL；否则返回稳定 `409 ACTIVITY_TIME_CONFLICT`（Topic 不存在仍为 404）。拒绝响应和日志不得包含原始 URL。
- 结束或归档后的任何失败不得改变 revision、participantCount 或名单。

### FR-PHASE-003 归档与未举行

- `POST /archive` 仅允许 `ENDED`。未来或进行中调用返回 `409 ACTIVITY_TIME_CONFLICT`；归档内容、状态、revision 与名单保持不变。
- `UPCOMING` 的“取消排期”沿用既有语义：清空日历、地点、会议入口和报名，回到 `CLAIMED`。
- `LIVE` 禁止取消排期，避免活动进行中突然消失或关闭入口。
- `ENDED` 可使用同一 `POST /unschedule`，但页面动作改称“未举行 / 重新排期”，确认文案明确旧报名会被清空；服务端原子清空排期、地点、会议入口和全部旧报名，回到 `CLAIMED`，随后由协调者重新排期。失败不得部分清理。
- `unarchive` 保留既有原排期；恢复为 `SCHEDULED` 后立即按原时间派生阶段。历史异常的未来归档被撤销后会成为 `UPCOMING`，但新请求不能再创建未来归档。

### FR-PHASE-004 编辑边界

- PATCH 必须区分 dirty 字段。普通内容字段继续按 SPEC-005 的 revision 规则更新。
- `LIVE` / `ENDED` 禁止 PATCH `scheduledAt`、`duration`；允许修正 `room` / `meetingUrl`，但 `ENDED` 的真实入口仍不可读取。
- 服务端必须在执行 SQL 写入前读取同一 Topic 并校验当前阶段；校验与 revision CAS 共同生效，不能只依赖页面隐藏字段。

## 4. 页面操作逻辑

### 4.1 列表卡与日历

- `UPCOMING`：徽标“已排期”；显示报名、可用时加入会议、生成海报、取消排期和编辑；不显示“完成归档”。
- `LIVE`：徽标“进行中”；显示报名/取消报名、可用时加入会议和普通编辑；不显示海报、取消排期或归档。时间与时长在编辑表单中不可修改，并说明“活动进行中，排期已锁定”。
- `ENDED`：徽标“待归档”；显示只读“查看参与”、完成归档、“未举行 / 重新排期”和普通编辑；不显示报名、会议或海报。时间与时长不可修改。
- `ARCHIVED`：保持“已经归档”、查看参与和撤销归档；不得显示会议入口。
- `ARCHIVED` 可按 SPEC-002/033 修正历史时间与时长，但候选活动结束不得晚于该次归档时刻；该规则不等同于恢复为未来活动。
- 月历和周历使用相同阶段徽标/动作可用性；事件主体仍进入编辑，不得把失效动作藏在编辑错误后。

### 4.2 无刷新边界变化

- 页面维护轻量当前时间，并在最近一个可见活动的开始/结束边界到达时重新计算；最长兜底刷新间隔 30 秒。
- 跨入 `LIVE` 时移除海报/取消排期/归档，保留报名与会议；跨入 `ENDED` 时关闭会议和报名写入口，显示待归档动作。
- 若弹窗打开期间越过边界，提交仍由服务端权威拒绝；客户端收到 `ACTIVITY_TIME_CONFLICT` 后关闭失效弹窗、同步列表/统计并给出明确提示，不保留看似成功的陈旧 UI。

### 4.3 文案

- “排期已过”改为阶段准确的“进行中”或“分享已结束，等待归档”。
- `ENDED` 的重置动作不得沿用模糊的“取消排期”，使用“未举行 / 重新排期”，确认页明确删除旧报名和旧会议信息。
- 归档入口只在活动结束后出现，继续使用“沉淀本期收获 / 完成归档”。

## 5. API 错误与并发

- 新增稳定错误：
  - `400 ACTIVITY_TIME_INVALID`：新排期或改期不在未来、或时间数据非法；
  - `409 ACTIVITY_TIME_CONFLICT`：当前活动阶段不允许该动作，响应含用户可读 message，可包含非敏感 `phase`。
- 404、401、428、412 的优先级继续遵循 SPEC-005：鉴权与 If-Match 先行；实体不存在和 revision 冲突不得被阶段错误掩盖。
- 对带 If-Match 的动作，服务端先在同一写入边界确认实体与 revision，再判断阶段；陈旧 revision 返回 412，当前 revision 的非法阶段返回 409。
- 每个请求只捕获一次权威 `now` 用于该动作的所有阶段判断，测试通过注入时钟确定性覆盖毫秒边界。

## 6. 验收矩阵

### 6.1 纯函数与 API（注入时钟）

以 `start`、`end=start+duration` 为固定边界：

1. `start-1ms` 为 UPCOMING；报名、取消报名、会议入口、海报资格、改期和取消排期允许，归档拒绝。
2. `start` 与 `end-1ms` 为 LIVE；报名、取消报名和会议入口允许；海报、归档、取消排期和时间 PATCH 拒绝。
3. `end` 为 ENDED；报名、取消报名和会议入口拒绝且不返回 URL；归档允许；“未举行 / 重新排期”原子清空旧报名与会议字段并回到 CLAIMED。
4. schedule at `now` / past 均 400；未来 archive 409；ARCHIVED meeting-access 409。
5. 所有拒绝路径逐项断言 revision、Topic 字段、participantCount 和名单不变，日志/响应不含 URL。
6. revision 不匹配与阶段冲突同时存在时返回 412；缺失 If-Match 仍为 428。

### 6.2 桌面 Chrome 与 Pixel 7

1. 分别加载 UPCOMING / LIVE / ENDED / ARCHIVED 夹具，断言徽标、说明和动作严格符合矩阵；不通过点击隐藏动作来“测试”服务端。
2. UPCOMING 完成报名、取消、会议、海报；LIVE 完成迟到报名与会议；ENDED 只读名单后归档，另一条 ENDED 走“未举行 / 重新排期”且人数归零。
3. 页面不刷新跨过开始边界后自动从“已排期”变“进行中”，对应动作即时切换；纯函数/API 负责精确结束边界，浏览器至少验证加载后的 ENDED 表达。
4. 由另一客户端或时钟边界造成的陈旧报名/会议/归档提交收到阶段冲突时，页面关闭失效弹窗、同步权威结果并保留清晰反馈。
5. 月历/周历与列表不出现阶段矛盾；按钮触控目标、焦点恢复、口令解锁和移动端无横向溢出回归通过。

## 7. 非目标

- 不新增持久化 `LIVE` / `COMPLETED` 状态，不运行定时数据库任务。
- 不自动归档、不自动发送提醒、不推断活动是否实际举行。
- 不实现候补、容量、签到、通知或外部日历同步。
- 本轮不修叠层 AccessModal 所有权和周历报名入口；两项已作为第 11 轮后续 P1/P2 登记，完成本规格后继续循环。
