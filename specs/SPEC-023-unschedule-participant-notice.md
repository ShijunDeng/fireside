# SPEC-023：取消排期前的报名名单与通知闭环

- 状态：`Accepted`
- 创建：2026-09-02
- 优先级：P1
- 关联：SPEC-004、SPEC-005、SPEC-007、SPEC-009、SPEC-013、SPEC-014、SPEC-017

## 1. 用户风险

未来活动“取消排期”和结束后“未举行 / 重新排期”都会在同一事务永久删除全部报名。当前确认层只说“报名会被移除”，不显示受影响人数/姓名，也没有复制或通知确认。协调者确认后系统内再无联系人，参与者可能仍按旧日程赴会。

系统没有个人账号、联系方式或消息通道，因此不能假装自动通知；成熟的最小闭环是让已解锁协调者在名单删除前取得可操作快照，并明确承担线下通知责任。

## 2. 产品决策

- 新增受保护的“取消排期影响”读取，只向有效协作会话返回当前公开 Topic 快照和报名姓名；响应 `no-store`，不包含会议入口或其他隐私字段。
- 打开取消/未举行确认后先读取权威影响快照。加载中或加载失败时禁止提交；有报名时显示精确人数和姓名，提供“复制通知名单”。
- 有报名时必须勾选“我已另行通知以上伙伴排期变化”才能提交；系统不发送消息，不把勾选状态持久化为虚假审计记录。零报名时明确说明无需通知，不显示强制勾选。
- 报名、取消报名和其他 Topic 更新都会推进 revision。提交使用影响快照的 revision；收到 412 时保留确认层，重新读取最新 Topic/名单、清除旧勾选并要求重新确认，不自动重放删除。
- 若活动已开始、已取消、已归档或已删除，继续使用现有状态/阶段冲突恢复，不允许名单读取变成生命周期旁路。

## 3. API 契约

### FR-IMPACT-023

- `GET /api/topics/:id/unschedule-impact` 需要有效协作会话，使用同一个 SQLite 只读事务读取 Topic 与按报名 ID 排序的名单。
- 不存在返回 404；不是 `SCHEDULED` 返回 `409 TOPIC_STATE_CONFLICT`；合法时返回 `{ topic, participants }`，其中 `topic.meetingUrl` 永远为 `null`。
- 响应固定 `Cache-Control:no-store`；匿名或失效会话返回 401，且不得泄漏目标是否存在、状态或名单。
- GET 零写入，不推进 revision/updatedAt/排序版本。
- 既有 `POST /unschedule` 的事务与删除语义不变；其 If-Match revision 必须来自当前影响快照。

## 4. 页面契约

1. 确认层显示议题、原北京时间、动作类型、报名数和完整姓名列表；极端姓名安全换行，不横向溢出。
2. “复制通知名单”至少包含议题、原时间、动作类型、人数和逐行姓名；复制成功/失败有可见反馈，失败时名单文本仍可手动选择。
3. 有报名时通知确认未勾选，提交按钮禁用；勾选后可提交。名单因 412 刷新时，焦点到可见提示，勾选复位，按钮重新禁用。
4. 加载失败保留 dialog 并提供显式重试；关闭后不应用迟到响应。
5. 成功反馈说明排期/名单已移除以及线下通知责任已确认；零报名不声称通知了任何人。
6. 另一协作者完成取消排期后，仍打开的报名弹窗在收到更高 Topic revision 时关闭并显示“排期已取消、报名名单已清空”；不能继续展示已被事务删除的姓名或人数。

## 5. 验收矩阵

1. API：匿名 401、缺失 404、错误状态 409、合法快照/no-store/脱敏/稳定顺序/零写入。
2. API：读取后另一人报名使旧 revision 的 unschedule 返回 412 且名单和排期不变；用新快照 revision 才能成功并原子清空名单。
3. E2E 桌面与 Pixel：N 人名单可见、复制、未勾选禁用、勾选后成功；取消与“未举行”两种文案正确。
4. E2E：确认期间并发报名触发 412，dialog/名单保留并刷新，旧确认复位，用户第二次明确提交才成功。
5. E2E：影响读取失败可重试，表单/滚动锁/焦点不丢；极端姓名与移动触控不横溢。
6. 双客户端交错：A 打开名单，B 取消排期；A 同步完整列表后关闭陈旧名单、卡片进入准备中、页面无旧姓名并给出可感知结果。
7. 全量类型检查、单元/API、生产构建和跨端无重试浏览器回归通过。

## 6. 非目标

- 不新增短信、邮件、IM webhook、个人账号或已送达回执。
- 不保留取消后的报名历史；若未来需要审计留存，必须另行定义数据最小化、保存期和删除权。
- 不把“复制”或本地勾选包装成系统已自动通知。
